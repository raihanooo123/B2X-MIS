---

## 1. Purpose

The order pad is the **primary buying tool** for trade customers. A buyer restocking a shop does not browse a catalogue; they work down a list of things they always buy, type quantities, and submit. Everything about this screen is optimised for that.

It is also the single clearest failure of the reference system, which presents 920 SKUs as **92 pages of 10 rows** with a keyword search box and no filters, no sorting, and no way to add by SKU code. A buyer with a 60-line order cannot use it.

---

## 2. What the reference system gets wrong

Each row is a requirement in disguise.

| Reference system | Consequence | Requirement here |
|---|---|---|
| 10 rows per page, 92 pages | A 60-line order spans dozens of page loads, losing state | 50–100 rows per page, state preserved |
| `OFFSET` pagination | Degrades linearly; page 92 is slow | Keyset pagination (02 §9 rule 8) |
| Keyword search only | Cannot narrow by category, brand or stock | Full facet set |
| No sorting | Cannot work down a list in any useful order | Sort by name, code, price, stock |
| No SKU entry | A buyer with a written list must search each item | Paste SKUs or upload CSV |
| Flat unit price only | No indication a larger quantity is cheaper | Break table inline per row |
| No pack choice | Cannot express "3 outers" | Pack selector per row |
| Placeholder images | Buyers select by sight | Thumbnail per row, from bulk ingest |
| No reorder | Every order rebuilt from scratch | Saved lists and reorder |
| Page reload per add | Unusable at 60 lines | No round trip per quantity change |

## 4. Screen specification

### 4.1 Layout

```
┌──────────────────────────────────────────────────────────────────────┐
│ Order Pad            [Saved lists ▾] [Reorder ▾] [Paste SKUs] [CSV]  │
├──────────────────────────────────────────────────────────────────────┤
│ Search …   Category ▾  Brand ▾  ☐ In stock  ☐ On offer   Sort ▾      │
├──────────────────────────────────────────────────────────────────────┤
│ img │ Name / SKU      │ Pack ▾    │ Price   │ Breaks      │ Stk │ Qty │ Line │
│ ▢   │ Grater 4-side   │ Outer 144 │ £123.84 │ 144+ £0.92  │ 696 │ [ 3]│ £371 │
│     │ LTC1179         │           │ /outer  │ 1440+ £0.86 │     │     │      │
├──────────────────────────────────────────────────────────────────────┤
│ Sticky footer:  18 lines · 2,304 units · £1,842.60 net               │
│ ✓ Free delivery reached   ·   Spend £158 more for 3% off  [Basket →] │
└──────────────────────────────────────────────────────────────────────┘
```

### 4.2 Row contents

| Element | Behaviour |
|---|---|
| Thumbnail | From `media` for the SKU, else the product, else a neutral placeholder. Lazy loaded, WebP/AVIF with `srcset` |
| Name and SKU code | `sku_code` shown always — buyers reference it verbally and in writing |
| Pack selector | Sellable packs for the SKU, ascending by `base_units`, defaulting to `is_default_sell`. Single-pack SKUs render as static text, not a one-option dropdown |
| Price | Per selected pack, derived per 03 §5. Unit price shown beneath in smaller type |
| Break table | Up to three break rows for the selected pack, translated from base units. Row four collapses to "more" |
| Stock | `available_base_qty` in the selected pack's units. Colour band, never colour alone: numeral plus label |
| Quantity | Numeric stepper in **packs**, stepping by 1 pack. Empty by default, never 0 |
| Line total | Recomputed locally on every change, no round trip |

### 4.3 Stock display

Stock is shown in the **selected pack's units**, because that is what the buyer is ordering in.

| Condition | Display |
|---|---|
| `available >= 1 pack` | "12 outers" (floor of available ÷ base_units) |
| `0 < available < 1 pack` | "Part case only" with the base-unit figure |
| `available = 0`, backorder allowed | "On backorder" plus `incoming` ETA if known |
| `available = 0`, no backorder | "Out of stock" with a **back-in-stock signup** — the reference system's clearest lost demand |
| `is_stock_tracked = 0` | No figure shown |

Exact figures are shown rather than banded ("low stock"). Trade buyers order against real numbers and banding invites a phone call.

## 5. Pricing behaviour

### 5.1 Local recomputation

The three queries in 03 §8 return the **full break table** for every visible row. Consequently:

- Changing a quantity recomputes unit price, line total, order subtotal, free-delivery progress and spend-break progress **entirely client-side**.
- No request per keystroke. No debounce race. No flicker.
- The client is a calculator over server-supplied data, never an authority. On submit the server re-resolves everything and the server's figures win. A client/server mismatch is logged as a defect, not silently accepted.

### 5.2 Break crossing feedback

When a quantity crosses a break, the row indicates it immediately: the unit price updates and the crossed break row is marked. When a quantity sits just below one, the row nudges — *"add 1 more outer for £0.86/unit"* — computed from `nextBreakQty` (03 §4.5).

### 5.3 Spend break progress

The footer shows distance to the next order-wide threshold (03 §7A.6): *"Spend £158 more for 3% off your order"*. When reached it confirms, and shows the next tier if one exists. Contract-priced lines are excluded from the qualifying subtotal where `applies_to_contract_lines = 0`, and the footer says so rather than appearing to miscount.

## 6. Validation rules

Enforced client-side for immediacy **and** server-side for authority. Client validation is a courtesy; the server is the rule.

| Rule | Source | Behaviour |
|---|---|---|
| MOQ | `skus.moq_base_qty` | Below minimum: row flagged, minimum stated in pack terms |
| Order increment | `skus.order_increment_base_qty` | Non-multiple: rounded up to the next valid multiple, with a visible note |
| Max order | `skus.max_order_base_qty` | Capped, with a note |
| Pack sellable | `packs.is_sellable` | Non-sellable packs never offered |
| SKU active | `skus.status` | Inactive SKUs excluded from results entirely |
| Stock | `available_base_qty` | Over-available: warned, not blocked, unless backorder is disallowed — then capped |
| Minimum order value | Configured threshold | Checkout blocked below it, with the shortfall stated and progress shown in the footer |

**Rules surface at entry, not at checkout.** A buyer who enters 60 lines and discovers at checkout that four break a case-multiple rule has to find and fix them. Flagging at entry costs nothing and prevents that.

## 7. Bulk entry

### 7.1 Paste SKUs

A textarea accepting one line per item, tolerant of real-world input:

```
LTC1179, 3
LTC1180  12
LTC1181;5
LTC1182            (quantity omitted → 1 pack, default pack)
```

Comma, semicolon, tab or whitespace separated. Case-insensitive on the code, though `sku_code` itself is stored case-sensitively (02 §2.6) — matching normalises for lookup only.

Returns a **reconciliation screen before anything enters the basket**:

| Outcome | Presentation |
|---|---|
| Matched | Name, pack, quantity, resolved price, line total |
| Matched, quantity adjusted | Highlighted with the reason (MOQ or increment) |
| Not found | Listed with the input line, plus close-match suggestions |
| Inactive or discontinued | Listed separately with status |
| Duplicate code in input | Merged, with the merge shown |

Nothing is added until confirmed. Partial confirmation is allowed: fix the failures, add the rest.

### 7.2 CSV upload

Same reconciliation. Expected headers `sku_code`, `quantity`, optional `pack_code`; header detection is case- and order-insensitive. A downloadable template is offered. A rejection report is downloadable so the buyer can correct their own file.

Files over 500 rows are processed on a queue with progress, rather than held in a request.

### 7.3 Saved lists and reorder

- **Reorder** — any past order becomes a starting basket. Unavailable or discontinued lines are flagged rather than silently dropped; a buyer must know what changed.
- **Saved lists** — named, company-scoped, shared across users on the account. Created from the current pad state or from a past order.
- Both land on the same reconciliation screen, for the same reason: the catalogue moves, and the buyer needs to see what moved.

## 8. Interaction detail

### 8.1 Keyboard

The difference between a usable and unusable pad at 60 lines.

| Key | Action |
|---|---|
| `Tab` / `Shift+Tab` | Next / previous quantity field, skipping non-inputs |
| `↑` / `↓` | Increment / decrement by one pack |
| `Enter` | Commit and move to the next row |
| `Esc` | Revert the current field |
| `/` | Focus search from anywhere |

Quantity fields are reachable in document order with no keyboard traps. Focus is never stolen by an async update.

### 8.2 Mobile

- Card layout below the table breakpoint; quantity stepper and pack selector remain thumb-sized (44 px minimum targets).
- Sticky footer total persists.
- **Barcode scanning** via the device camera: scan a shelf barcode, matched against `skus.barcode_ean` then `packs.barcode`, and the row is focused with the pack preselected from whichever matched. This is the in-aisle restocking workflow and it is the reason mobile matters here.
- Offline tolerance is a Phase 4 PWA concern, noted not built.

### 8.3 State persistence

Pad state persists server-side in `carts` and `cart_lines`, not in browser storage. A buyer interrupted mid-order resumes on another device. Cart lines hold `sku_id`, `pack_id` and `base_qty`, so a pack change is a line update rather than a delete and re-add.

### 8.4 Rep order-on-behalf

A rep selecting a customer sees that customer's resolved prices, tier, contract lines, credit position and stock. An unmistakable banner states whose account is active. Every action writes `orders.placed_by_user_id` alongside `user_id` — the audit trail distinguishing "the customer ordered this" from "a rep ordered this for them".

## 9. Data and queries

Per 03 §8, **three queries per page regardless of row count**:

| Query | Index | Budget |
|---|---|---|
| Q-A candidate price list ids for the company | `price_lists_company_idx` / `price_lists_tier_idx` | cached, 5 ms |
| Q-B all break rows for those lists × those SKUs | `price_list_items_resolve_idx` (covering) | 15 ms |
| Q-C stock levels for those SKUs | `stock_levels` PRIMARY | 10 ms |

Plus one paginated catalogue query for the rows themselves, using `products_cat_active_idx` and the facet indexes (02 §10, Q3–Q4). Search is in-database — weighted `tsvector` plus `pg_trgm` for typo tolerance (02 §5.4a) — so there is no external engine to be stale or unavailable, and a filter change is one query rather than a query plus an index lookup.

Pagination is **keyset on `(name, id)`** or the active sort column plus `id`. `OFFSET` is not used: at 92 pages it degrades linearly, which is a measurable part of why the reference system's pad is slow.

**Total budget: under 800 ms warm for a 100-row page** (Doc 03 §14 criterion 4).

## 10. Edge cases

| Case | Behaviour |
|---|---|
| Price changes while the pad is open | Server re-resolves on submit; if a line's price moved, the buyer is shown the difference and confirms before the order is placed. Never silently repriced |
| Stock drops to zero while the pad is open | Surfaced at submit as a shortfall per line (04 §4.6), not as a generic failure |
| SKU deactivated while in the cart | Line flagged, blocked from checkout, cart otherwise intact |
| Pack deleted while in the cart | Line falls back to the default sell pack, `base_qty` preserved, change shown |
| Two users on one company account editing the same cart | Last write wins on a line; a notice states another user changed the cart |
| Quantity entered in the thousands by typo | Warned above a configurable threshold; not blocked — some orders genuinely are that large |
| Filter returns zero rows | Empty state naming the active filters with one-tap clearing. The query is logged to the zero-result report, which is how catalogue gaps get found |
| Spend break qualifies then the basket shrinks | Footer updates immediately; the discount is never shown as locked in before submit |

## 11. Test matrix

**Functional:** pack selection changes price, stock display and line total consistently · break crossing updates unit price and marks the row · MOQ and increment adjustments applied and visible · paste parses all four separator styles · paste reconciliation classifies matched, adjusted, not-found, inactive and duplicate correctly · CSV rejection report downloadable · reorder flags discontinued lines · saved list round-trips · barcode matches both `skus.barcode_ean` and `packs.barcode` · rep banner present and `placed_by_user_id` written.

**Numeric:** client-computed subtotal equals the server's re-resolution for 1,000 generated baskets, exactly. Any mismatch is a test failure, not a tolerance.

**Performance:** 100-row page under 800 ms warm · Q-B `EXPLAIN` shows `Using index` · no N+1 (query count asserted constant as row count varies from 10 to 100) · keyset pagination query time flat from page 1 to page 50.

**Accessibility:** full keyboard entry of a 20-line order with no mouse · all quantity fields reachable in document order · no keyboard trap · 44 px minimum touch targets · stock state conveyed by text as well as colour · screen-reader announcement on price change.

---

## 12. Acceptance criteria

1. A 60-line order is entered in a single page session, keyboard only, with no page reload.
2. Pasting 60 SKU codes with quantities produces a reconciliation screen listing every line's outcome, and adds only what the buyer confirms.
3. Break tables are visible on every row without interaction, and unit price updates locally on quantity change with no request.
4. Client and server subtotals agree exactly across 1,000 generated baskets.
5. All MOQ, increment and stock rules surface at entry; nothing new appears for the first time at checkout.
6. 100-row page renders under 800 ms warm, with a constant query count as row count varies.
7. Free-delivery and spend-break progress are both live in the footer and update on every change.
8. Out-of-stock rows offer back-in-stock signup.
9. A rep can open any assigned customer's pad, see their resolved prices, and place an order recorded against both users.
10. WCAG 2.1 AA verified for the whole screen, including the mobile card layout.
