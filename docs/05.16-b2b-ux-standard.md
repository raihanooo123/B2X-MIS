## 1. Benchmark and shared design system

These are pattern references, not an instruction to copy branding or import libraries:
[Shopify B2B](https://help.shopify.com/en/manual/b2b/getting-started/features) for quick
ordering and clear terms; [Amazon Business](https://business.amazon.com/en/solutions/compliance-management/guided-buying)
for buying-policy explanations and approval visibility; [Faire](https://www.faire.com/support/articles/4415920212123)
for applicant guidance; [Stripe Dashboard](https://docs.stripe.com/dashboard/search)
for searchable financial records; [Linear](https://linear.app/docs/select-issues)
for keyboard selection and actions. The requirements below are our proposed standard,
not claims that every benchmark implements them identically.

Use existing `resources/css/app.css` semantic tokens, `tailwind.config.js`, Figtree,
Tailwind and locally generated `resources/js/components/ui/` shadcn/ui components.
Reuse the storefront's neutral surfaces, restrained primary colour, border treatment,
rounded controls and visible focus from `StorefrontLayout.tsx`. No new UI library,
separate brand palette, font or chart/table framework. Extend existing components
when a primitive is absent. Staff administration remains Filament v3, using its
existing controls and the same spacing, states, policies and acceptance criteria;
this standard does not replace Filament with a second admin app.

## 2. Shell, headers and responsive layout

Trade Inertia pages share a shell: sidebar with Dashboard, Order pad, Orders, Quotes,
Returns and Account; top bar with active company, company switch, search/help and
profile. Policy-gate Approvals, Financial documents and Dropship. Reps get their own
book navigation and a persistent named-company/acting-for banner. Staff keep the
Filament shell. Every page has a breadcrumb, one h1, short optional explanation and
one primary action; secondary actions use a menu. Detail pages put status and
reference beside the title and totals in a summary panel.

| Viewport | Required layout |
|---|---|
| 390 px | Sidebar becomes a labelled drawer; 16 px gutters; single column; header actions wrap; tables become labelled cards with the same essential data/actions. Sticky totals cannot hide inputs or focus. |
| 768 px | Drawer/compact navigation; 24 px gutters; one or two columns only when fields fit; cards remain until all essential table columns fit. |
| 1280 px | 240 px sidebar; 24 px content gutters; main/detail summary columns; desktop tables with explicit column priorities. |
| 1440 px | Same shell, 32 px gutters; content max-width 1440 px; readable forms max-width 720 px; dense operational tables may use remaining width. |

No horizontal **page** scroll at any width, including long SKU/address/error text and
200% zoom. Wrap or disclose secondary columns rather than squeezing text. Do not
remove information on mobile; secondary detail is expandable. Test all four widths.

## 3. Lists and data tables

Semantic table with labelled sticky header below the top bar; sticky elements cannot
obscure keyboard focus. Sortable headers expose direction with `aria-sort`; default
sort and unique tie-breaker are defined by each module. Filter toolbar includes
search, status/date filters, applied-filter chips and Clear. Debounce search 250 ms.
Use cursor/keyset **Load more**, usually 50 rows, maximum 100; reset the cursor on
sort/filter changes. No OFFSET pagination. Bound cursor to company, filters and sort.

Useful recurring operational views (approvals, orders, rep book, containers) support
named **personal saved views**; shareable views are deferred. Initially URL-backed
filters and browser-local saved names are sufficient, scoped to user/company/module,
cleared on logout and containing no customer/financial payloads. Save status/date/sort
preferences only; do not persist free-text customer/reference searches in browser storage. This requires no
new database table. Saved buying lists are a different, company-shared domain object.

Bulk actions have checkboxes/card selection, a selected-count bar and explicit
"loaded rows only" scope; never imply unseen records are selected. Revalidate each
record server-side and return per-record results. Money/destructive bulk operations
require confirmation and cannot silently skip failed rows. Status always has text
(e.g. "Overdue") plus colour/icon; colour alone never carries meaning.

## 4. States, forms and keyboard use

Every screen must specify: meaningful first-use empty state with a permitted action;
filtered-empty state with Clear filters; skeletons matching eventual geometry;
recoverable error with Retry and a safe reference; success state with the resulting
record/action. Preserve entered data after errors. Buttons show pending state and
prevent duplicate submissions. Action toasts use a polite live region; actionable
errors also remain inline, not only in a disappearing toast.

Forms have persistent labels, help text, field-level validation and an error summary
linked to invalid fields. On failed submit focus the summary/first error. Destructive
or money actions use a confirm dialog stating company, affected records, amount,
consequences and primary verb; default focus is Cancel. Trap and restore dialog focus.
Server confirmation is authoritative; never optimistically show paid/approved/refunded.

Order pad: Tab follows rows/fields; Enter advances quantity entry without placing an
order; Ctrl/Cmd+Enter opens review only. Approvals: optional j/k row navigation and
Enter opens detail, never approves. `/` focuses list search and `?` opens shortcut
help only outside inputs/contenteditable; shortcuts can be disabled. Escape closes
menus/dialogs and restores focus. No shortcut overrides browser/system commands.
Skip link, logical DOM order, visible focus and complete keyboard operation are required.

## 5. Accessibility and formatting

Meet WCAG 2.1 AA: semantic landmarks/headings, accessible labels, 4.5:1 normal-text
contrast, 3:1 large-text/control contrast, screen-reader status announcements and
reduced-motion support. All interactive touch targets are at least **44 × 44 px**;
dense tables can pad the hit area. Automated axe checks supplement manual keyboard,
zoom, contrast and screen-reader checks; they do not prove WCAG compliance alone.

Right-align quantities, percentages and money with `tabular-nums`; labels left-align.
Use `£1,234.56` for GBP document amounts, explicit Net/VAT/Gross labels and en-GB
formatting; e4 unit-price detail may show four decimals with a scale label. Display
dates as `05/10/2026`, timestamps in Europe/London with timezone where consequential;
API timestamps remain UTC ISO 8601. Never use floating-point money arithmetic or
parse formatted strings back into amounts. Unknown cost remains unavailable, not zero.

## 6. Performance and acceptance

07 §2 is authoritative: pad 100 rows p95 800 ms; orders query/page 20/900 ms;
checkout preview 400 ms; quote-detail query 30 ms; container apportionment 500 ms;
rep statement 50 ms; queued PDF 3 s. LCP <2.5 s on 4G, INP <200 ms, CLS <0.1,
initial JS gzip <250 KB; pad quantity-to-total <50 ms with no network. Batch prices,
stock and relationships, assert constant query count and EXPLAIN relevant hot paths.
Virtualise only with accessible navigation and proven need. Optimistic UI is allowed
for reversible list names/preferences/cart edits with rollback and version conflict
handling; credit, stock commitment, approval, settlement and finalisation await success.

Every new screen needs deterministic Playwright screenshot baselines at **390 and
1440 px** (populated plus empty/loading/error/success fixtures), responsive functional
checks at 768/1280, no page overflow and keyboard/focus tests. Run axe on page and
open dialogs at mobile/desktop: **zero serious or critical violations**, and resolve
other failures against WCAG AA. Include policy variants and cost/privacy redaction.
Record 07 budget measurements and query-count checks. These are proposed acceptance
gates; existing CI is not claimed to run screenshots or axe today.
