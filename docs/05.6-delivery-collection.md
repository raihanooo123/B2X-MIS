## 1. Purpose

Carriage is where a wholesale order's economics are decided. On a pallet of £2 kitchenware, delivery can be a third of the line value, and getting it wrong means either losing the order or losing money on it.

This module turns four rules that currently live in prose — and contradict each other — into resolvable data:

1. Free mainland delivery over a threshold
2. Free warehouse collection over a lower threshold
3. Northern Ireland "priced case by case"
4. A minimum order value

---

## 2. What the reference system gets wrong

### 2.1 The contradiction worth resolving first

The reference system states two different minimum figures:

| Source | Statement |
|---|---|
| FAQ | Free mainland UK delivery over **£500 + VAT**; below that, carriage quoted per address |
| Terms & Conditions | *"reduced our minimum order from £1500 to £1000"* |

These are almost certainly **two different rules that have been conflated**, not one rule stated inconsistently:

- **Minimum order value** — the smallest order the business will accept at all
- **Carriage-paid threshold** — the value above which delivery is free

A £600 order would be accepted and delivered free under the FAQ, and rejected outright under the T&Cs. One of those pages is wrong, and it is the legally binding one that says £1,000.

**This specification models them as two independent configured values**, because they are two independent business rules and conflating them in the schema guarantees the confusion persists. Which value belongs to which rule is a question for the client (§15 Q1) — but the model does not force a choice, and either answer is a configuration change.

### 2.2 The rest

| Reference system | Consequence | Requirement here |
|---|---|---|
| Carriage "quoted manually per delivery address" | Every sub-threshold order needs a human | Rated automatically from zone and weight |
| Northern Ireland "case by case" | Delay and inconsistency on every NI order | BT zone with its own rate table |
| No Highlands or islands handling | Loss-making deliveries to IV, KW, HS, ZE, IM, JE, GY | Explicit zones with surcharges |
| No weight modelling | Carriage cannot be computed | Weight from pack data (02 §5.6) |
| No pallet logic | Pallet-quantity orders rated as parcels | Parcel/pallet decision from volumetrics |
| Collection offered, not bookable | Customers arrive unannounced | Bookable slots with capacity |
| Thresholds stated net, displayed ambiguously | Buyer sees £0.98 and expects £0.98 | Net/gross explicit throughout |

## 4. Zone resolution

### 4.1 UK postcodes, and why prefix matching alone fails

A UK outward code is an **area** (1–2 letters) plus a **district** (1–2 digits, occasionally with a trailing letter): `IV51`, `BT9`, `PO31`, `EC1A`.

Naive string-prefix matching breaks immediately. Isle of Wight is `PO30`–`PO41`, but mainland Portsmouth is `PO1`–`PO22` — and `PO3` is a prefix of both `PO30` and mainland `PO3`. Matching on `"PO3"` would put Portsmouth on the Isle of Wight.

So zones are defined by **area plus an optional district range**, not by string prefixes.

### 4.2 `delivery_zones`

```sql
CREATE TABLE delivery_zones (
  id                            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  code                          text        NOT NULL,
  name                          text        NOT NULL,
  country_code                  char(2)     NOT NULL DEFAULT 'GB',
  is_mainland                   boolean     NOT NULL DEFAULT true,
  is_serviceable                boolean     NOT NULL DEFAULT true,
  requires_manual_quote         boolean     NOT NULL DEFAULT false,
  carriage_paid_threshold_minor bigint,
  transit_days                  smallint,
  position                      smallint    NOT NULL DEFAULT 0,
  created_at                    timestamptz NOT NULL DEFAULT now(),
  updated_at                    timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT delivery_zones_code_uq UNIQUE (code)
);

CREATE INDEX delivery_zones_country_idx ON delivery_zones (country_code)
  WHERE is_serviceable;
```

`carriage_paid_threshold_minor` is nullable: NULL means inherit the global threshold from `system_configurations`. A zone can therefore raise its own threshold — free delivery over £500 to the mainland but over £1,200 to the Highlands — without a second mechanism.

Launch zones:

| Code | Name | Postcode definition | Mainland |
|---|---|---|---|
| `GB_MAINLAND` | UK Mainland | Default fallback | Yes |
| `GB_NI` | Northern Ireland | `BT` | No |
| `GB_HIGHLANDS` | Scottish Highlands | `IV`, `KW1`–`KW14`, `PA21`–`PA40`, `PH15`–`PH50` | Yes |
| `GB_SCOT_ISLES` | Scottish Islands | `HS`, `ZE`, `KW15`–`KW17`, `PA41`–`PA80` | No |
| `GB_IOW` | Isle of Wight | `PO30`–`PO41` | No |
| `GB_SCILLY` | Isles of Scilly | `TR21`–`TR25` | No |
| `GB_IOM` | Isle of Man | `IM` | No |
| `GB_CHANNEL` | Channel Islands | `JE`, `GY` | No |

Channel Islands and Isle of Man are outside UK VAT. `requires_manual_quote` is set on `GB_SCILLY` and `GB_CHANNEL` at launch — low volume, high variance, not worth rating badly.

### 4.3 `delivery_zone_postcodes`

```sql
CREATE TABLE delivery_zone_postcodes (
  id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  zone_id       bigint   NOT NULL REFERENCES delivery_zones (id) ON DELETE CASCADE,
  area          text     NOT NULL,
  district_from smallint,
  district_to   smallint,
  -- narrowest matching range wins; a whole-area rule always loses
  specificity   integer GENERATED ALWAYS AS (
                  CASE WHEN district_from IS NULL THEN 9999
                       ELSE district_to - district_from END
                ) STORED,

  CONSTRAINT delivery_zone_postcodes_range_uq
    UNIQUE NULLS NOT DISTINCT (area, district_from, district_to),
  CONSTRAINT delivery_zone_postcodes_range_chk CHECK (
      (district_from IS NULL AND district_to IS NULL)
   OR (district_from IS NOT NULL AND district_to IS NOT NULL
       AND district_to >= district_from)
  )
);

CREATE INDEX delivery_zone_postcodes_resolve_idx
  ON delivery_zone_postcodes (area, specificity)
  INCLUDE (district_from, district_to, zone_id);
```

`district_from`/`district_to` both NULL means the whole area — `BT`, `IV`, `IM`.

### 4.4 Resolution query

Parse the outward code into area letters and district number, then:

```sql
SELECT zone_id
FROM   delivery_zone_postcodes
WHERE  area = :area
  AND  (district_from IS NULL
        OR :district BETWEEN district_from AND district_to)
ORDER BY specificity ASC
LIMIT  1;
```

**`specificity` is a stored generated column**, so it is indexable (02 §2.5) and the narrowest matching range wins with no sort. A whole-area rule gets `9999`, so it always loses to any range that also matches. `PO31` therefore resolves to `GB_IOW` (range width 11) rather than to any broader `PO` rule, and `PO3` resolves to the mainland fallback because it falls outside 30–41.

No match resolves to `GB_MAINLAND`. Non-GB countries resolve on `country_code` and are `requires_manual_quote` at launch.

Resolved zone is cached against `addresses.delivery_zone_id` (02 §4.5) at address save, and re-resolved if the postcode changes. Budget: 5 ms cold, then free.

## 5. Rates

### 5.1 Weight and method

Consignment weight comes from pack data (02 §5.6):

```
line_weight_g = pack_qty × packs.gross_weight_g
                (fallback: base_qty × skus.unit_weight_g)
consignment_weight_g = Σ line_weight_g
```

Where neither is populated, the order is flagged **unrateable** and routed to manual quote rather than rated on a guess. A carriage figure invented from missing data is worse than asking.

The parcel/pallet decision:

```
pallet_equivalents = Σ (pack_qty / (packs_per_layer × layers_per_pallet))
method = pallet_equivalents >= configured_threshold  (default 0.5)
         OR consignment_weight_g > configured_max_parcel_weight  (default 30 kg)
         ? 'pallet' : 'parcel'
```

Both thresholds live in `system_configurations`.

### 5.2 `delivery_rates`

```sql
CREATE TABLE delivery_rates (
  id                 bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  zone_id            bigint    NOT NULL REFERENCES delivery_zones (id),
  method             text      NOT NULL DEFAULT 'parcel',
  weight_range       int4range NOT NULL,
  price_net_minor    bigint    NOT NULL,
  per_extra_kg_minor bigint,
  tax_class_id       bigint    NOT NULL REFERENCES tax_classes (id),
  validity           tstzrange NOT NULL DEFAULT tstzrange(now(), NULL, '[)'),
  status             text      NOT NULL DEFAULT 'draft',
  created_at         timestamptz NOT NULL DEFAULT now(),
  updated_at         timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT delivery_rates_method_chk CHECK (method IN
    ('parcel','pallet','courier_next_day','collection')),
  CONSTRAINT delivery_rates_status_chk CHECK (status IN ('draft','active','archived')),
  CONSTRAINT delivery_rates_price_chk  CHECK (price_net_minor >= 0),
  CONSTRAINT delivery_rates_bands_chk  CHECK (NOT isempty(weight_range)),
  CONSTRAINT delivery_rates_validity_chk CHECK (NOT isempty(validity)),

  -- neither overlapping weight bands nor overlapping validity windows
  CONSTRAINT delivery_rates_no_overlap
    EXCLUDE USING gist (zone_id WITH =, method WITH =,
                        weight_range WITH &&, validity WITH &&)
    WHERE (status = 'active')
);

CREATE INDEX delivery_rates_resolve_idx
  ON delivery_rates USING gist (zone_id, method, weight_range, validity)
  WHERE status = 'active';
```

- Weight bands are **rows**, exactly as price breaks are rows (03 §3.1). Adding a band is an `INSERT`.
- `max_weight_g` NULL means the top band, with `per_extra_kg_minor` applied above `min_weight_g`.
- `delivery_rates_resolve_idx` mirrors `price_list_items_resolve_idx` (02 §6.4): descending `min_weight_g` so the first row read is the applicable band, `price_net_minor` trailing to make it covering.
- Sentinel validity dates, per 02 §6.3, keeping the predicate indexable.
- Carriage carries its own `tax_class_id`. It is a taxable supply and is not assumed to match the goods' rate.

### 5.3 Resolution

```sql
SELECT price_net_minor, per_extra_kg_minor, min_weight_g, tax_class_id
FROM   delivery_rates
WHERE  zone_id = :zone AND method = :method AND status = 'active'
  AND  :now BETWEEN valid_from AND valid_to
  AND  min_weight_g <= :weight_g
  AND  (max_weight_g IS NULL OR :weight_g <= max_weight_g)
ORDER BY min_weight_g DESC
LIMIT  1;
```

```
shipping_net_minor = price_net_minor
                   + (per_extra_kg_minor IS NULL ? 0
                      : round_half_up(max(0, weight_g − min_weight_g)
                                      × per_extra_kg_minor / 1000))
```

One rounding operation, integer arithmetic, per 03 §6.

## 6. Thresholds

Four independent configured values, all in `system_configurations` (02 §2.7), all scopeable to company or location:

| Key | Default | Meaning |
|---|---|---|
| `orders.minimum_value_net_minor` | **TBC — see §15 Q1** | Smallest order accepted at all |
| `delivery.carriage_paid_threshold_net_minor` | 50000 (£500) | Free mainland delivery above this |
| `collection.free_threshold_net_minor` | 20000 (£200) | Free collection above this |
| `delivery.zone_threshold_override` | per zone | Via `delivery_zones.carriage_paid_threshold_minor` |

**All are net of VAT**, matching the business's stated terms, and every customer-facing display says so explicitly. The reference system shows `£0.98` with no indication it is net, which is the kind of ambiguity that produces a dispute at invoice.

Evaluation against the **post-discount net subtotal** — after item pricing and after the spend-break pass (03 §7A). A spend break that drops an order below the carriage-paid threshold does remove free delivery, and the cart shows this happening rather than surprising the buyer at checkout.

### 6.1 Minimum order enforcement

| Condition | Behaviour |
|---|---|
| Subtotal below minimum | Checkout blocked. Shortfall stated, progress shown in the order pad footer (05.1 §5.3) |
| Rep or admin placing the order | Override permitted with a reason code, written to the audit log |
| Order is a replacement under an RMA | Minimum does not apply. A replacement is not a new sale |
| Collection rather than delivery | Separate minimum, if configured; defaults to the same value |

## 7. Collection slots

### 7.1 Schema

```sql
CREATE TABLE collection_slots (
  id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  location_id  bigint      NOT NULL REFERENCES locations (id),
  slot_date    date        NOT NULL,
  start_time   time        NOT NULL,
  end_time     time        NOT NULL,
  capacity     smallint    NOT NULL DEFAULT 1,
  booked_count smallint    NOT NULL DEFAULT 0,
  status       text        NOT NULL DEFAULT 'open',
  note         text,
  created_at   timestamptz NOT NULL DEFAULT now(),
  updated_at   timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT collection_slots_slot_uq UNIQUE (location_id, slot_date, start_time),
  CONSTRAINT collection_slots_status_chk CHECK (status IN ('open','full','closed')),
  CONSTRAINT collection_slots_times_chk  CHECK (end_time > start_time),
  CONSTRAINT collection_slots_capacity_chk CHECK (booked_count <= capacity),
  CONSTRAINT collection_slots_count_chk  CHECK (booked_count >= 0)
);

-- partial: the booking picker only ever queries open future slots with room
CREATE INDEX collection_slots_available_idx
  ON collection_slots (location_id, slot_date, start_time)
  INCLUDE (capacity, booked_count)
  WHERE status = 'open';

CREATE TABLE collection_bookings (
  id                   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  collection_slot_id   bigint      NOT NULL REFERENCES collection_slots (id),
  order_id             bigint      NOT NULL REFERENCES orders (id),
  company_id           bigint      REFERENCES companies (id),   -- NULL for a public or guest order (amended 2026-10-04)
  status               text        NOT NULL DEFAULT 'booked',
  collector_name       text,
  vehicle_registration text,
  collected_at         timestamptz,
  created_at           timestamptz NOT NULL DEFAULT now(),
  updated_at           timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT collection_bookings_order_uq UNIQUE (order_id),
  CONSTRAINT collection_bookings_status_chk CHECK (status IN
    ('booked','collected','no_show','cancelled'))
);

CREATE INDEX collection_bookings_slot_idx ON collection_bookings (collection_slot_id)
  WHERE status = 'booked';
CREATE INDEX collection_bookings_company_idx
  ON collection_bookings (company_id, created_at DESC);
```

*Amended 2026-10-04 (05.15 §9 A4), signed off 2026-10-04.* `collection_bookings.company_id` was `NOT NULL`, written when every buyer had a company. A public customer's or guest's collection has none. Such a booking reaches its customer through `order_id`, which is `NOT NULL` and unique, and the order names the customer (02 §26.1), as payments do (02 §19). No check is added: `order_id` already guarantees an owner. `collection_bookings_company_idx` holds the NULL rows but is only queried for a company. The table is not migrated yet, so this changes the DDL above rather than adding an `ALTER`.

`collection_slots_capacity_chk CHECK (booked_count <= capacity)` makes overbooking structurally impossible. `collection_bookings_order_uq` makes booking idempotent — a retried checkout cannot book twice, the same pattern as `credit_holds_order_uq` and `stock_allocations_identity_uq`.

### 7.2 Booking concurrency — extends the global lock order

Booking a slot inside checkout adds a second lockable row type. Per the reasoning in 05.2 §8.2, it joins the single global lock order rather than creating a parallel one:

```
1. companies         (credit, one row)
2. collection_slots  (one row, if collection)
3. stock_levels      (ascending sku_id, location_id, batch_id)
4. inserts
```

Slot sits second because it is one row, cheap, and failing it avoids taking stock locks at all. The `CHECK` constraint is the backstop; the lock is what produces a clean error rather than a constraint violation surfacing to the customer.

### 7.3 Behaviour

- Slots generated from a recurring weekly pattern, configurable per location, with date exceptions for closures.
- Booking horizon and lead time configured — default 14 days ahead, minimum 2 hours notice.
- **Stock is already allocated at order placement** (04 §4.7). The slot schedules the handover; it does not reserve the goods. A customer with no slot still has their stock held.
- Rescheduling releases the old slot and books the new one in one transaction.
- `no_show` recorded after the slot passes uncollected. The stale-allocation reaper does **not** release a paid collection order — the customer has bought the goods. Unpaid no-shows follow the standard hold window.
- The warehouse sees the day's bookings and stages orders ahead of arrival — which is the operational point of slots.

## 7A. Public collection and pay at collection (S5b) — signed off 2026-10-05

> **Status: signed off 2026-10-05**, with the product owner's changes: slots exist as generated rows and are locked in invariant 6's order (§7A.1, §7A.4); a daily cash report (§7A.6a); the 14-day cancellation runs from collection day and the pre-contract information names pay at collection (§7A.3); Q-C1 and Q-C4 decided (§7A.15). Builds §7 for everyone (it isn't built for anyone yet, ROADMAP §23A), adds public and guest collection (05.15 §6.1, A4), and adds **pay at collection**, a product-owner decision of 2026-10-05: a signed-in, verified customer books a slot and pays **cash** at the counter. Card at collection needs a terminal and is out of scope until the POS module (ROADMAP §25, parked).

### 7A.1 Slots

- **Weekly pattern per location**, as the location-scoped configuration key `collection.slot_pattern` (`json`, 02 §2.7), with no new table:

  ```json
  { "mon": [{"start": "09:00", "end": "10:00", "capacity": 4}, {"start": "10:00", "end": "11:00", "capacity": 4}],
    "tue": [], "sat": [{"start": "09:00", "end": "12:00", "capacity": 6}] }
  ```

  Times are UK local time (Europe/London). A day that is missing or empty has no slots.
- **Generation:** a daily job (`collection:generate-slots`) creates `collection_slots` rows up to `collection.booking_horizon_days` ahead (default 14). It is idempotent on `collection_slots_slot_uq`. It never changes or deletes a slot that has bookings. A pattern change affects only days not yet generated.
- **Slots are rows, always.** A booking refers only to a `collection_slots` row that the generator has already created. Checkout and staff screens never create a slot on the fly. A slot id that doesn't exist, is closed, is full or has started is refused with 422 `slot_unavailable`. This keeps the slot a real, lockable row for invariant 6 (§7A.4) and keeps `collection_slots_capacity_chk` the backstop.
- **Closures:** staff close a slot or a whole day (status `closed`) in Filament. Bookings on a closed slot are moved by staff to another slot (§7A.9). A booking is never orphaned.
- **Offered to the customer:** open slots with room, starting at least `collection.min_notice_minutes` from now (default 120), within the horizon. They come from `collection_slots_available_idx` (§9).
- A slot's **end instant** is `(slot_date + end_time)` in Europe/London, converted to UTC. That instant drives payment deadlines (§7A.5), so DST is handled once, here.

### 7A.2 Checkout with collection (every customer, guests included)

1. **Fulfilment:** delivery or collection. Collection shows the location (one at launch) and its slots (§7A.1).
2. **Customer details:** collection needs no delivery address (decided Q-C1).
   - **Trade:** the company's default billing address (02 §4.5) is snapshotted to `order_addresses` as `billing`, as for any trade order.
   - **Public customers and guests:** no address is required. The customer is named by the account or `guest_email` (02 §26.1). For a guest, the name and phone they enter are kept on a `billing` `order_addresses` row only if they give an address. Otherwise identification at the counter uses the order number and email (§7A.6).
3. **Charge:** the `collection` method in `delivery_rates`, free above `collection.free_threshold_net_minor` (§6). For a consumer, `standard_shipping_net_minor` is 0 (02 §26.3). Rule G (GB only, 05.15 §6.1) doesn't apply to a collection, because there is no delivery country. The VAT rate is GB's.
4. **Payment:** card for everyone; **pay at collection** for those who qualify (§7A.3); on-account and BACS for trade as today.
5. **Place:** one transaction in the global lock order (§7A.4). **Collection allocates only at the slot's location.** This amends 04 §4.2 step 2: for a collection order, the candidate sources are the slot's `location_id`, never another site, because the customer is standing at that counter. A shortfall there rolls back the whole transaction, as for any shortfall.

### 7A.3 Pay at collection — who and how much

All of these must hold, checked in the checkout preview (shown as a reason) and again in the place-order transaction:

| Rule | Detail |
|---|---|
| Switched on | `collection.pay_at_collection.enabled` = true for the location (default **false**) |
| Signed in, never a guest | A public customer (`user_id`, no company), or a trade user ordering for their company |
| Email verified | 05.13 §11, for trade users and public customers alike |
| Not suspended | No active row in `pay_at_collection_suspensions` (§7A.11) for the user (public) or the company (trade) |
| Within the limit | Order `total_gross_minor` ≤ `collection.pay_at_collection.max_order_gross_minor` (default 30000, £300). **Gross**, because cash is paid gross. A trade buyer, who sees net prices, is shown the limit as "£300.00 inc VAT" |
| Collection | `fulfilment_type = 'collection'` with a booked slot |
| Trade account in good standing | Treated as prepay (05.2 §8.1): no credit hold. Refused if the company is suspended and the suspension forbids prepay |

The order is placed as `status = 'confirmed'`, `payment_status = 'unpaid'` and `payment_method = 'cash_at_collection'`. It is **not** `pending_payment`, so the 2-hour stale-allocation reaper (04 §9) never touches it. Its hold is governed by §7A.5 instead.

**Button and pre-contract wording** (CCR reg. 14(3), 05.15 §7.1): "Place order — pay £X.XX in cash at collection". The pre-contract information (05.15 §7.1) names the payment arrangement **"Pay cash at collection"**. With the confirmation email, it states the slot, the location, the amount, "cash only", and the payment deadline (§7A.5) with what happens after it.

**Cancellation period.** For a consumer, the 14-day cancellation period runs from the **day of collection**: the day the customer, or someone they name, collects the goods (CCR reg. 30(3)). That is `collection_bookings.collected_at` as a UK date (05.15 §7.2, 05.4 §13.3). Before collection, the order can be cancelled at any time (05.4 §13.2). For an unpaid pay-at-collection order there is nothing to refund. The pre-contract information and the confirmation email say both.

### 7A.4 Lock order

The global order (02 §11.1, §7.2), extended for the paths that start from an existing order:

```
1. companies            (credit, when the path moves credit)
2. orders               (paths that act on an existing order: payment, handover, expiry, reschedule, cancel)
3. collection_slots     (one row; two rows in ascending id when rescheduling)
4. collection_bookings  (the order's one booking)
5. shipments → stock_allocations (ascending id) → stock_levels (02 §11.1 order) → stock_serials
6. payments
7. number_sequences     (last, 02 §11.3)
```

**Invariant 6 holds on every path (confirmed at sign-off).** CLAUDE.md invariant 6 and 02 §11.1 fix `companies → collection_slots → stock_levels`:

- **Placement** takes exactly that sequence: `companies` (only when the order moves credit), then the one `collection_slots` row (only for a collection), then `stock_levels` ascending (`sku_id`, `location_id`, `batch_id NULLS FIRST`), then inserts.
- **Paths that act on an existing order** take `orders` between `companies` and `collection_slots`.
- No path locks `orders` after a slot, or a slot after `stock_levels`. Every path's lock sequence is therefore an ordered subsequence of the list above, and the invariant-6 triple keeps its relative order everywhere.

The generated-SQL lock-order test (§7A.16) asserts this for placement, cash recording, handover, expiry, reschedule and cancellation. Invoicing keeps `companies → orders` and runs after commit in its own transaction, as it does for card capture.

### 7A.5 Holding the stock, and automatic expiry

- **The stock stays allocated** from placement until the order is collected, cancelled or expires.
- **Payment deadline:** at booking, `collection_bookings.payment_due_by` = the slot's end instant + `collection.pay_at_collection.grace_minutes` (default 60). It is snapshotted, so a later change to the setting doesn't move an existing deadline (02 §2.7). It is NULL for prepaid bookings.
- **Expiry sweep** (`collection:expire-unpaid`, every 5 minutes, one worker, no overlap). For each booking with `status = 'booked'`, `payment_due_by < now()` and an unpaid order, in its own transaction:
  1. `orders` FOR UPDATE. Re-check `payment_status = 'unpaid'` and the booking still `booked`; otherwise skip (payment won the race).
  2. Booking → `no_show`, `no_show_at = now()`. The slot's `booked_count` is unchanged: the slot is in the past and its capacity was used.
  3. Cancel the order through `OrderCancellationService` with reason `collection_expired`: `deallocation` movements, `status = 'cancelled'`, `cancellation_fee_minor = 0`. There's nothing to refund, because nothing was paid.
  4. Count the customer's pay-at-collection no-shows (§7A.11); at the limit, insert a suspension.
  5. After commit: `collection.expired` to the customer, plus `collection.pay_at_collection_suspended` if they were suspended.
- **Race with the counter:** recording a cash payment locks the same `orders` row first. Whoever commits first wins. A payment that arrives after the sweep is refused ("this order expired and its stock was released"). A sweep that arrives after the payment skips the order. Payment is accepted right up to the sweep, so the grace period is real slack for a late customer.
- **Prepaid collections are unchanged** (§7.3): a card-paid no-show keeps its stock, the booking becomes `no_show` when staff mark it, and staff contact the customer.

### 7A.6 At the counter — payment, then handover

Warehouse screen **Collections** (React, `dispatch` permission): today's and overdue bookings, search by order number, name or phone, and the order's lines, allocation and staging bin.

1. **Identify** the collector: the customer, or someone they name (`collector_name`). A guest shows the order number and the email it was placed with (05.5 §12).
2. **Record cash** (pay-at-collection orders only). Staff confirm "£X.XX received in cash". The amount is the order's `total_gross_minor`, exactly: no part-payments, and change is handled at the till drawer. In one transaction: `orders` → `collection_bookings` FOR UPDATE, re-check (unpaid, booked, not expired), then insert `payments` (`gateway = 'cash'`, `type = 'payment'`, `status = 'captured'`, `amount_minor = total`, `captured_at = now()`, `recorded_by_user_id`). The order becomes `paid` (`OrderPayments::markPaid`, same transaction). Audited as `payment.cash_recorded`.
3. **Receipt or invoice** is issued immediately after commit, **synchronously**, by `InvoiceService` in its own transaction. A public order gets a receipt (`RCP-`); a trade order gets a VAT invoice with terms `prepay`. Both carry the cash payment's allocation (02 §14.5.4). The counter screen shows the number and offers print and email. The PDF is rendered off the request (05.5 §7.3).
4. **Handover** = collection dispatch (04 §7.2, 05.5 §7.1). **Refused unless the order is paid**: `payment_status = 'paid'`, enforced in `DispatchService` and asserted by tests. This applies to every collection, card or cash. **The one exception is an on-account trade order** (`payment_method = 'on_account'`, `payment_status = 'on_account'`): its credit was held at placement and it is invoiced on dispatch like any on-account order (§7A.2 step 4), so it may be handed over unpaid *(amended 2026-10-05, product-owner decision)*. Dispatch movements are written. The booking becomes `collected`, with `collected_at` and `handed_over_by_user_id`. `collected_at` is the possession day for a consumer's 14-day cancellation (05.4 §13.3).
- **Wrong amount keyed:** before handover, staff with `accounts` role may void the cash payment (status `voided`, reason in the audit log `payment.cash_voided`) and record it again. After handover, a mistake is a refund (§7A.10), never an edit.
- **Picking may start before payment**, so goods can be staged before the customer arrives. Only the handover waits for payment.
- **Cash-up:** the daily cash report (§7A.6a).

### 7A.6a Daily cash report (end-of-day cash-up)

A Filament page, **Collections → Daily cash report**, for staff with `accounts` role or the `dispatch` permission:

- **Filters:** location (one at launch), and a UK calendar day (default today, Europe/London: midnight to midnight local time, so DST days are 23 or 25 hours).
- **Per staff member:** the cash recorded that day by each `recorded_by_user_id`, with the count of payments, the gross total and the count and total of voided entries.
- **Day total:** cash recorded minus voids, which is what the drawer should hold from pay at collection. Cash refunds paid at the counter (§7A.8) are shown as a separate line, subtracted for the net figure.
- **Detail:** every cash payment of the day (time, order number, customer, amount, recorded by, voided by and why), newest first, with a link to the order.
- **Source:** `payments` with `gateway = 'cash'` (`type` `payment` and `refund`), joined to `orders` and the booking's location, filtered on `captured_at` (voids on their audit time). Integer totals (invariant 1).
- **Export:** CSV of the detail, for the cash-up sheet.
- No new table and no stored totals: the report reads the payment rows, so it can't drift. Its query is reviewed with EXPLAIN at realistic volume; a covering index is proposed only if the plan needs one.

Till-drawer counting and variance recording are POS (ROADMAP §25, parked) and are not part of this report.

### 7A.7 Rescheduling and cancelling

- **Customer reschedule** (order page) before the slot starts, to an available slot within the horizon. In one transaction: `orders` → both `collection_slots` rows in ascending id → booking. Then decrement the old slot, increment the new one, and recompute `payment_due_by`. **Pay-at-collection orders may reschedule once** (`reschedule_count`, Q-C3), because each move extends the stock hold. Prepaid orders have no limit.
- **Customer cancels** before collection:
  - A consumer uses 05.4 §13.2. For an unpaid cash order that means no refund, and the booking is `cancelled` with its slot decremented.
  - A trade customer goes through 05.10.
- **The business closes a slot:** staff move each booking to another slot (a staff reschedule, not counted against the customer) and the customer gets `collection_slot.cancelled` with the new time. If the customer refuses, the order is cancelled.

### 7A.8 Refunds of a cash-paid order

After collection, a consumer's cancellation or fault refund (05.4 §13.6) must go back by "the same means of payment" unless they expressly agree otherwise (CCR reg. 34(7)–(8)). So it is either:

- **cash at the counter** when the goods come back in person: a `payments` refund row, `gateway = 'cash'`, `recorded_by_user_id`; or
- **bank transfer** with the customer's recorded agreement: `gateway = 'bacs'`, paid by accounts (05.4 §13.6).

Q-C4 asks for legal confirmation. Trade cash refunds follow 05.4 §7.5A (account balance) as for any trade credit note.

### 7A.11 No-shows and suspension

- **Counted:** the customer's bookings with `status = 'no_show'` on orders with `payment_method = 'cash_at_collection'`, with `no_show_at` inside the last `collection.pay_at_collection.no_show_window_days` days (default 365) **and** after the customer's last lifted suspension. A trade customer is counted per **company**; a public customer per **user**. Prepaid no-shows don't count: they have paid.
- **Limit:** `collection.pay_at_collection.no_show_limit` (default 2). Reaching it inserts a suspension (`reason = 'no_shows'`, automatic), inside the sweep's transaction. `ON CONFLICT DO NOTHING` on the active-suspension index makes a second insert harmless.
- **Effect:** pay at collection is no longer offered to that customer. Card payment, collection and everything else are unaffected.
- **Lifting:** a staff member with `accounts` role lifts it in Filament with a reason (audited `collection.pay_at_collection_reinstated`). Counting restarts from the lift. Staff may also suspend manually with a reason (`reason = 'manual'`).

`'cash'` is already in `payments_gateway_chk`. A voided cash payment (status `voided`) drops out of `payments_cash_order_uq`, so the corrected amount can be recorded.

**New table, proposed amendment to 02:**

```sql
CREATE TABLE pay_at_collection_suspensions (
  id                    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id               bigint      REFERENCES users (id),
  company_id            bigint      REFERENCES companies (id),
  reason                text        NOT NULL,
  no_show_count         smallint,
  suspended_at          timestamptz NOT NULL DEFAULT now(),
  suspended_by_user_id  bigint      REFERENCES users (id),   -- NULL = automatic
  note                  text,
  lifted_at             timestamptz,
  lifted_by_user_id     bigint      REFERENCES users (id),
  lift_reason           text,

  CONSTRAINT pay_at_collection_suspensions_owner_chk CHECK (
    (user_id IS NOT NULL AND company_id IS NULL) OR (user_id IS NULL AND company_id IS NOT NULL)),
  CONSTRAINT pay_at_collection_suspensions_reason_chk CHECK (reason IN ('no_shows','manual')),
  CONSTRAINT pay_at_collection_suspensions_manual_chk CHECK (
    reason <> 'manual' OR (suspended_by_user_id IS NOT NULL AND note IS NOT NULL)),
  CONSTRAINT pay_at_collection_suspensions_auto_chk CHECK (
    reason <> 'no_shows' OR no_show_count IS NOT NULL),
  CONSTRAINT pay_at_collection_suspensions_lift_chk CHECK (
    lifted_at IS NULL OR (lifted_by_user_id IS NOT NULL AND btrim(lift_reason) <> ''))

-- at most one active suspension per customer; also the checkout eligibility lookup
CREATE UNIQUE INDEX pay_at_collection_suspensions_user_active_uq

```

- History is kept: a lift sets `lifted_*` and never deletes, and the next suspension is a new row.

## 8. Cart and checkout integration

The order pad footer and basket show, live:

```
Subtotal (net)                          £1,842.60
Delivery — UK Mainland, pallet             £48.00
─────────────────────────────────────────────────
Spend £157.40 more for free delivery
Spend £157.40 more for 3% off your order
```

Rules:

- Carriage is computed and shown **before** the payment step, never revealed at the end.
- Free-delivery progress and spend-break progress (03 §7A.6) are both shown, and coincide often enough that they must not be confused with one another.
- Where the zone is `requires_manual_quote` or the consignment is unrateable (missing weight data, no matching band, no carriage tax rate), carriage shows as *"quoted separately"* and the order is **blocked**: the customer is told *"We'll quote you for delivery to this address before you order"*, and neither the order nor a card authorisation is created. Carriage is never charged as £0 because it could not be rated.

  *Amended 2026-09-25.* This section originally accepted such orders into a carriage-quote queue. That queue does not exist yet, and accepting a card order before its total is known would mean either charging an incomplete total or authorising an amount the customer never saw. Until a quote queue and a "pay once quoted" flow are specified, unrateable orders are refused at preview, at card authorisation and at `POST /checkout`.
- Changing the delivery address re-resolves zone and rate immediately.
- Carriage is snapshotted to `orders.shipping_net_minor` at placement and never re-resolved — same principle as prices (03 §3.4).

| Case | Behaviour |
|---|---|
| `PO3` vs `PO31` | `PO3` → mainland, `PO31` → Isle of Wight. The §4.4 resolution test case |

## 12. Acceptance criteria

1. All eleven zone fixtures resolve correctly, with `PO3`/`PO31` explicitly verified.
2. Minimum order value and carriage-paid threshold are two independent configured values, adjustable per company and location from the admin UI.
3. Carriage is computed and displayed before the payment step on every order.
4. An order with missing weight data is routed to manual quote, never rated on a guess.
5. Free-delivery and spend-break progress are shown distinctly and update live.
6. A spend break that drops the subtotal below the carriage-paid threshold restores carriage visibly in the cart.
7. D1 passes: no slot is ever overbooked, across 100 repetitions.
8. The extended global lock order (companies → slot → stock) is asserted by test, with zero deadlocks.
9. Carriage is snapshotted at placement and never re-resolved.
10. Every customer-facing threshold and price states whether it is net or gross.
