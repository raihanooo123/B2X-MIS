## 1. Purpose

Doc 04 specifies what happens to the **ledger**. This document specifies what happens to the **people and the goods** — the screens a warehouse operative uses, in what order, with what validation, and what the system refuses to let them do.

It is where batch codes, expiry dates and serial numbers are actually captured. Every traceability guarantee in Doc 04 depends on data entered here. If goods-in is slow or awkward, operatives work around it, and the traceability becomes fiction while still appearing to work.

So the governing constraint is not correctness alone. **It is correctness that is faster than the workaround.**

---

## 2. What the reference system gets wrong

It has no warehouse module. Stock is a mutable number an administrator edits.

| Reference system | Consequence | Requirement here |
|---|---|---|
| Stock edited directly as a number | No audit trail; "why is this wrong" unanswerable | Every change is a ledger movement with cause and actor |
| No goods-in screen | Receipts keyed as stock adjustments, unlinked to any PO | Receipt against a PO line, with variance capture |
| No batch or expiry capture | Recall impossible; expired stock sold | Mandatory capture where the SKU requires it |
| No pick list | Orders picked from a printed order confirmation | Pick lists grouped by bin, showing batch and serial |
| No dispatch event | Stock decremented whenever someone remembers | Atomic dispatch transaction (04 §7.2) |
| No partial dispatch | Split shipments handled on paper | `part_dispatched` with per-line tracking |
| Pack quantities not modelled | Operatives convert cases to units by hand | Every quantity entered in packs, converted on entry |

## 4. Goods-in

### 4.1 Sources

| Source | Reference | Cost |
|---|---|---|
| Purchase order | `purchase_order_lines` | From the PO line; landed cost apportioned on container arrival |
| Container | `containers` → several POs | Freight and duty apportioned across the container (Phase 3) |
| Manual receipt | none | Cost entered or omitted; flagged for purchasing review |
| Customer return | `rma_lines` | No cost movement; handled by 05.4 §7.4 |
| Inter-location transfer | `transfers` | Cost carried from the origin |

### 4.2 Screen flow

```
1. Identify the source     → scan PO number, container reference, or "manual"
2. Select the line          → search by SKU code or scan a case barcode
3. Enter quantity in packs  → pack selector defaults to the PO line's pack
4. Conditional capture      → batch / expiry / serials, per tracking_mode
5. Assign location and bin
6. Confirm                  → one transaction (04 §7.1)
7. Repeat, or close the receipt
```

Quantity is always entered **in packs**, with the base-unit equivalent shown live: *"3 outers = 432 units"*. An operative counting a pallet counts cases. Requiring unit entry invites the mental arithmetic that produces a receipt of 43 instead of 432.

### 4.3 Conditional capture

Driven by `skus.tracking_mode` and `requires_expiry` (02 §5.5). Fields appear only when they apply — this is the difference between a fast screen and one that gets circumvented.

| `tracking_mode` | Captured |
|---|---|
| `none` | Quantity, location, bin |
| `batch` | Plus batch code, and expiry if `requires_expiry = 1` |
| `serial` | Plus one serial per base unit |
| `batch_and_serial` | Both |

Rules, all from Doc 04 §7.1 and enforced at the screen:

- A batch-tracked SKU **cannot be received without a batch code.** Rejected at entry, not accepted and corrected later. Corrected batch data is untrustworthy for a recall, which defeats the point of capturing it.
- `requires_expiry = 1` makes the expiry date mandatory. An expiry in the past, or beyond a configured sanity horizon, warns and requires confirmation — a mistyped year is the common error.
- Where `shelf_life_days` is set, expiry is **pre-filled** from the receipt date and remains editable. Most receipts are fresh stock and typing the date each time is waste.
- Serial capture supports scanning, pasting a supplier manifest, or importing a CSV. Pre-registered `expected` serials transition to `in_stock` rather than duplicating (02 §7.6).
- Duplicate serial for the same SKU is rejected by `stock_serials_sku_number_uq`. The screen says which receipt it was first seen on.

### 4.4 Variance

Over- and under-receipt against a PO line are both permitted, with a mandatory reason code from a closed list: `short_shipped`, `over_shipped`, `damaged_in_transit`, `supplier_substitution`, `miscount_corrected`, `other`.

Permitted because they happen. Suppliers short-ship. Containers arrive with crushed cases. A system that refuses to record reality gets a workaround — usually an operative keying the ordered quantity and adjusting later, which loses the supplier-performance data entirely.

Variance feeds a supplier report keyed on `purchase_orders.supplier_id`, which is the evidence for a conversation with the supplier.

### 4.5 Costs

Where the receipt carries cost, a `sku_costs` row is created (02 §6.6) at `e4` scale. Container receipts apportion freight and duty across lines by value or weight, configured per container — the detail is in 05.7.

Receiving without cost is allowed but flagged: without it, margin on everything sold from that receipt is unknown (03 §11).

### 4.6 After commit

`StockReceived` fires, triggering back-in-stock notifications (04 §8), search reindex, PO progress update, and backorder auto-allocation in `placed_at` order.

## 5. Picking

### 5.1 Pick list generation

A pick list is generated per shipment, not per order — one order may ship in two parcels on different days, and two orders may be picked together.

Sort order, in sequence:

1. `suggested_bin_id` in warehouse walk sequence (`bins.walk_sequence`)
2. SKU code, as a tiebreak within a bin

`suggested_bin_id` is **advisory** (04 §4.7). It comes from the allocation and exists to route the walk. A picker taking goods from a different bin is not an error and the system records what was actually taken, not what was suggested.

### 5.2 What a pick line shows

| Element | Why |
|---|---|
| Bin (suggested) | Where to walk |
| Thumbnail | Confirming the right item faster than reading a name |
| SKU code and name | Identification |
| Pack and quantity, in packs | "3 outers", not "432 units" |
| **Batch code** where batch-tracked | The specific batch allocated by FEFO (04 §5) |
| **Serial list** where serial-tracked | The specific units reserved at allocation (04 §6.1) |
| Expiry where captured | So an operative can see if something looks wrong |

Serials are reserved at allocation, not chosen at pick (04 §6.1). The pick list therefore names them, and:

- Scanning a serial not in `allocated` for this order is **blocked, not warned.**
- Substitution requires an explicit reassignment action, which rewrites the allocation and writes to the audit log.

This is strict on purpose. The alternative — letting a picker grab any unit — means the warranty and recall traces are wrong while appearing complete, which is worse than not having them.

### 5.3 Batch substitution

Picking a different batch than allocated is permitted via an explicit reallocation, which:

1. Releases the original batch allocation (`deallocation` movement)
2. Allocates the substituted batch (`allocation` movement)
3. Updates `stock_allocations.batch_id`
4. Writes to the audit log with actor and reason

Permitted because the FEFO-selected batch may be physically unreachable — buried behind a pallet. Never silent, because the delivery note and recall trace both depend on it.

**Until the audit log exists (02 §15, ROADMAP §0.6), decided 2026-09-25:** the substitution's `deallocation` and `allocation` movements carry the actor, reason code `batch_substitution` and a note naming both batches and the picker's reason, and a `BatchSubstituted` event fires after commit. Step 4's audit write is added when §15 is signed off. Serial-tracked lines cannot be substituted until allocation reserves serials (ROADMAP §4); they are short-picked instead.

### 5.4 Short picks

A picker finding fewer than allocated reports a short pick per line, with a reason: `not_found`, `damaged`, `wrong_location`, `quantity_short`.

The system then:

1. Records the actual picked quantity
2. Writes an `adjustment` movement for the discrepancy, with the reason code — the stock was never there, and the ledger must say so
3. Flags the order line for re-planning: allocate from another batch or location, or backorder the remainder
4. Raises a discrepancy for investigation

**A short pick is a stock-accuracy event, not just an order problem.** Treating it only as the latter is how systems drift away from reality while every individual order looks handled.

**As built, 2026-09-25:**

- Step 1 keeps the picked quantity on the allocation (`picked`), or releases it if nothing was picked. A `deallocation` and an `adjustment` movement, both with the reason, take the shortfall off `allocated` and `on_hand` together.
- A serial-tracked line's unscanned reserved serials go to `quarantined`, with their order line cleared: missing, not written off.
- Step 3's re-plan runs in its own transaction after the short pick commits. Its stock_levels keys cannot be locked in 02 §11.1's order while the shorted row is held. It re-plans from other eligible `(location, batch)` keys only, since `stock_allocations_identity_uq` also covers released rows. Serial-tracked lines are backordered, not re-planned, until allocation reserves serials.
- Step 4's discrepancy is the `adjustment` movement itself, plus a `ShortPickRecorded` event and a warning log. No separate table.

## 6. Packing

- Parcels recorded per shipment: quantity, weight, dimensions. Pack dimensions from `packs` (02 §5.6) pre-fill the calculation.
- Pallet builds computed from `packs_per_layer × layers_per_pallet`.
- A packing station scans each item into a parcel, verifying against the pick. Mismatches block completion.
- The delivery note generates from what was **packed**, not what was ordered — including actual batches and serials.

## 7. Dispatch

The atomic moment, specified in Doc 04 §7.2. This document adds the operational surface.

### 7.1 Dispatch types

| Type | Trigger | Notes |
|---|---|---|
| Delivery | Parcels handed to carrier | Tracking number captured; courier manifest generated |
| Collection | Customer collects at the counter | Identity and signature captured; stock was already allocated at placement (04 §4.7) |
| Dropship | Shipped to the customer's end customer | Blind packing note: no pricing, no our-branding (05.8) |

Collection dispatch matters here: because collection allocates at placement, the goods have been reserved possibly for days. The counter screen shows the allocation, and dispatch is a confirmation rather than a fresh availability check.

### 7.2 Partial dispatch

Supported throughout (04 §7.2). `order_lines.dispatched_base_qty < base_qty` with the remainder still allocated; order status becomes `part_dispatched`, recomputed after every shipment.

**As built, 2026-09-25 — what a shipment covers.** `stock_allocations` has no shipment column, and `shipment_lines` are written at dispatch (04 §7.2). A shipment's scope is therefore its order's active (`allocated`/`picked`) allocations at its location, with at most one open shipment per order and location. Dispatch requires every line in scope picked or short-picked (§12). It is idempotent on the shipment itself, which dispatches once. A prepaid order is released to the warehouse only once paid ("paid before dispatch").

The customer is notified per shipment, with what shipped and what remains — a wholesale customer receiving 8 of 12 cases needs to know the other 4 are coming and when, not wonder whether the order was wrong.

### 7.3 Invoicing

An invoice is raised per shipment by default, so a part-dispatched order produces two invoices and the customer is billed for what they have. Configurable (`invoicing.mode` = `per_shipment` or `on_completion`) via `system_configurations` (02 §2.7).

Invoicing converts the credit hold to credit used (05.2 §8.3), inside the same transaction.

**Amendment 2026-09-25 (signed off 2026-09-25) — prepaid orders.** Prepaid orders (card, BACS, prepay) are invoiced for the whole order when they are paid or placed, with `shipment_id` NULL: card orders when the payment is captured, BACS and prepay orders when they are placed. `invoicing.mode` applies only to on-account orders, which are invoiced at dispatch. Only on-account invoicing converts a credit hold, because a prepaid order takes none (05.2 §8.1).

A public customer's order gets a receipt rather than a VAT invoice (02 §21.2): the same document, with no payment terms or due date. It is issued only once the order is paid. A card receipt is issued at capture. A BACS or prepay receipt waits until the payment is recorded, because a receipt issued before payment would acknowledge money not yet received.

Every issued document is rendered to PDF off the request (07 P25, queued) and archived to `attachments` (02 §21.1). The archive is what the customer received; line detail is otherwise derived from `order_lines` (02 §14.5.2).

**Amendment 2026-09-25 (decided 2026-09-25) — per-shipment amounts and the credit hold.** Each per-shipment invoice bills each shipped order line's **pro-rata share, with the remainder going to the shipment that completes the line**, so a fully dispatched order's invoices sum to its totals to the penny. It is computed by cumulative rounding. For a line total T over `base_qty` B, with Q units dispatched up to and including this shipment, `cumulative(Q) = T` if Q ≥ B, else `round_half_up(T × Q / B)`. The shipment's share is `cumulative(Q) − cumulative(Q_before)`. This applies independently to `line_net_minor`, `line_tax_minor` and, for display, the line's discount. "Before" is the order's shipments dispatched earlier, by `(dispatched_at, id)`, so an invoice document reprints identically from `shipment_lines`. Carriage and its VAT go on the order's first invoice.

Each per-shipment invoice moves its total into `credit_used_minor` and reduces the order's credit hold by the same amount. The invoice that completes the order (status `dispatched`), or one whose total would exhaust the hold, consumes what is left of it (hold → `invoiced`). A hold remainder left by an undelivered shortfall is released when that remainder is cancelled (05.10). Implemented by `ShipmentInvoiceShares` and `InvoiceService::issueForShipment()`.

## 8. Stocktake

- A session per location, counting per `(sku, location, batch)`.
- **Trading continues during a count.** **Corrected 2026-09-26 (02 §24.1):** variances are computed against the level **as it stood when each line was counted**, reconstructed at posting from the movements since, with the delta shown for review. Otherwise every sale during the count appears as a variance. The earlier wording, "at posting time", produced exactly that: count 10, sell 2, post, and a variance of +2.
- Nothing is written until posting. A half-finished count cannot corrupt live stock.
- Posting writes `stocktake` movements in one transaction, each with a reason code.
- Blind counting is configurable: hide the expected figure so the operative counts rather than confirms.
- Serial-tracked SKUs reconcile by scanning; missing serials are listed individually rather than as a quantity variance. Scans are kept per serial in `stocktake_line_serials` (02 §24.2). A missing serial reserved to an order blocks posting until the order is short-picked.
- Every line with a nonzero variance needs a reason at posting, from 02 §24.3's list.

## 9. Devices and interface

Warehouse conditions, not desk conditions.

- **Scanning throughout.** SKU barcodes (`skus.barcode_ean`), case barcodes (`packs.barcode`), bin labels, RMA numbers, PO numbers, serials. Every screen that asks for an identifier accepts a scan.
- **Gloves and cold.** Touch targets 48 px minimum, above the 44 px used elsewhere. No hover-dependent interaction.
- **Keyboard-complete.** Every flow completable on a wedge scanner plus numeric keypad, no pointer.
- **Tolerant of poor connectivity.** Each confirmation is a single atomic request; a dropped response is safely retryable because receipts and dispatches are idempotent on their reference (see §10).
- **Legible at arm's length.** Larger base type; batch codes and serials in a monospaced face — `0`/`O` and `1`/`I` confusion in a batch code breaks a recall trace.

## 10. Idempotency

Warehouse screens get double-tapped and requests get retried on flaky wireless. Every operation carries a client-generated idempotency key, and:

- Receipt lines are idempotent on `(receipt_id, po_line_id, client_token)`, which is `goods_receipt_lines_idempotency_uq` (02 §23.2). `client_token` is the request's `Idempotency-Key`
- Dispatch is idempotent on `(shipment_id, client_token)`
- Serial scans are idempotent on `(order_line_id, serial_id)`

A retried request returns the original result rather than writing a second movement. This is the same guarantee `stock_allocations_identity_uq`, `credit_holds_order_uq` and `quotes_converted_order_uq` provide elsewhere — the pattern is now consistent across every module that writes money or stock.

## 12. Edge cases

| Case | Behaviour |
|---|---|
| Goods arrive with no PO reference | Manual receipt, flagged for purchasing to match |
| PO line received in a pack size not on the PO | Permitted; any sellable pack of the SKU accepted, `base_qty` is what matters |
| Batch code already exists for this SKU | Adds to the existing batch. Expiry must match, or it is a different batch and the screen says so |
| Expiry typed in the past | Warned; requires confirmation. May be legitimate for clearance stock |
| Serial already `in_stock` | Rejected with the prior receipt named |
| Pick list printed, then order cancelled | Pick list invalidated; picker notified on next scan of that shipment |
| Picker cannot find any of the allocated batch | Short pick, adjustment written, line re-planned from another batch |
| Dispatch attempted with an unpicked line | Blocked. Dispatch requires every line picked or explicitly short-picked |
| Collection customer arrives without their reference | Lookup by company and contact; identity confirmed at the counter |
| Two operatives receiving the same PO line simultaneously | Both succeed; receipts are additive, not exclusive. Variance computed against the PO total |
| Stocktake posted while an order allocates the same SKU | Serialised by the `stock_levels` row lock; variance reflects the post-allocation level |
| Barcode scans as an unknown value | Screen offers search rather than failing, and logs the unknown code for catalogue correction |

## 13. Test matrix

**Receipt:** batch-tracked SKU cannot be received without a batch code · `requires_expiry` blocks without a date · expiry pre-filled from `shelf_life_days` and editable · duplicate serial rejected naming the prior receipt · `expected` serial transitions to `in_stock` without duplication · variance recorded with a mandatory reason and appearing in the supplier report · quantity entered in packs converts correctly to `base_qty` for every pack level · receipt with cost creates a `sku_costs` row at `e4` scale.

**Picking:** pick list ordered by bin walk sequence · batch and serials shown per line matching the allocation · scanning an unallocated serial is blocked · batch substitution writes deallocation, allocation and an audit entry · short pick writes an `adjustment` movement with reason and re-plans the line.

**Dispatch:** dispatch decrements `on_hand` and `allocated` atomically · partial dispatch sets `part_dispatched` and leaves the remainder allocated · a dispatch retried with the same idempotency token writes exactly one movement set · invoice raised per shipment converts the credit hold to credit used.

**Stocktake:** trading during a count does not produce false variances · nothing is written before posting · serial reconciliation lists missing serials individually.

**Concurrency:** W1 two operatives receiving one PO line simultaneously — both persist, no lost update · W2 dispatch racing a cancellation — exactly one wins, `allocated` never negative · W3 stocktake posting racing an allocation — serialised, ledger and projection agree.

## 14. Acceptance criteria

1. A batch-tracked SKU cannot be received without a batch code, and a `requires_expiry` SKU cannot be received without an expiry, at the screen.
2. Every quantity in every warehouse screen is entered and displayed in packs, with the base-unit equivalent shown.
3. Pick lists are ordered by bin walk sequence and name the exact batch and serials allocated.
4. Scanning a serial not allocated to the order is blocked, and substitution requires an explicit logged reassignment.
5. A short pick writes an `adjustment` movement with a reason code and re-plans the order line.
6. Dispatch is atomic per Doc 04 §7.2, and a retried dispatch writes exactly one movement set.
7. Partial dispatch leaves the remainder allocated and notifies the customer of what shipped and what remains.
8. A stocktake runs without halting trading and produces no false variances from concurrent sales.
9. W1–W3 concurrency tests pass with ledger and projection in agreement.
10. Every flow is completable using only a wedge scanner and numeric keypad, with 48 px minimum targets.
