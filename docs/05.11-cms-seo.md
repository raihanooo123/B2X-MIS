## 1. Scope

**In this draft:**

- Legal and help pages the business edits in the admin panel: Privacy notice, Cookies, Delivery, Returns & cancellations, Contact (§2).
- The Cookies page and its cookie list, and the consent rule (§2.5).
- Head tags: titles, descriptions, canonical URLs, `robots` rules (§4).
- Structured data: `Product`, `BreadcrumbList`, `Organization` (§5).
- `/sitemap.xml` and `robots.txt` (§6).

**Not in this draft**, each a later section of this document:

- Arbitrary content pages (`/pages/{slug}`), home-page banners and promotional blocks (05.15 §5.1 "featured and promotional content arrives with the CMS").
- **Redirects from the reference system's URLs.** Needed before cut-over (05.15 §10), not before S7. They depend on the import mapping (08).
- A consent banner. Not needed while every cookie is strictly necessary (§2.5).

The **terms of sale** stay in `terms_versions` (02 §25.1). They are a legal record with their own acceptance trail, not CMS content. This document only adds the public page that shows them (§2.1).

## 2. Legal and help pages

### 2.1 The pages

A closed list at launch. Admins can edit the content of these pages but cannot add new ones, so every footer link points at a page the law or the storefront needs.

| `page_key` | Path | Content | Generated block (not editable) |
|---|---|---|---|
| `privacy` | `/privacy` | Privacy notice (UK GDPR Art. 13–14), written by the business's solicitor | — |
| `cookies` | `/cookies` | Short introduction | The cookie table (§2.5) |
| `delivery` | `/delivery` | Delivery areas, times, collection | — |
| `returns` | `/returns` | Returns & cancellations | The statutory statement (§2.3) |
| `contact` | `/contact` | Opening hours, directions, any free text | Contact and legal details from `brand.*` and `seller.*` (05.15 §3.1, 02 §21.3) |
| *(terms)* | `/terms` | The current `sale` version from `terms_versions`, rendered read-only | Version label and effective date |

- Paths are fixed routes, not a catch-all, so a page can never shadow `/c`, `/p`, `/cart` or any other route.
- **A page with no published version returns 404,** and the footer leaves its link out (05.15 §8.1). `/terms` follows the same rule for `sale`.
- Every page uses the storefront shell (05.15 §3.2) and is indexable (§4.2).

### 2.2 Drafts, versions and publishing

Every published version is kept, never edited. A privacy notice or a returns statement is evidence of what a customer was told on a given date: UK GDPR accountability (Art. 5(2)) and CCR 2013 Sch. 2. It follows the same pattern as `terms_versions`.

- **One editable draft per page**, held on the page row (§3). Saving a draft changes nothing the public sees.
- **Publish** copies the draft into a new immutable version with an effective time (now, or later, never in the past), its SHA-256 and the publisher. The public sees the version with the latest `effective_from <= now()`.
- **A mistake** is corrected by publishing a new version. Versions cannot be edited or deleted, enforced by the same `reject_row_mutation()` trigger as 02 §25.1.
- **Body format:** Markdown, rendered on the server by the same renderer as the terms of sale. Raw HTML is escaped, and links are allowed only to `http`, `https`, `mailto` and `tel`.
- **Title and meta description** are versioned with the body, so a reprint of version 3 shows version 3's heading.

### 2.3 The statutory statement on Returns & cancellations

05.15 §7.2 requires the return-cost statement on this page, and the checkout and email already generate it (`PreContractInformation`). The page renders that same generated block **after** the editable text, and the admin cannot remove it. This makes the page, the checkout and the email say the same thing by construction. It cannot drift if someone edits the page.

### 2.4 Admin screen

- **Filament → Content → Pages** (`CmsPageResource`). Access is `admin` role only, through `CmsPagePolicy`. There is no separate authorisation path (CLAUDE.md).
- **List:** each of the five pages, with its draft state, the version in force and any scheduled version.
- **Edit:** Markdown editor with a live preview inside the storefront shell, title and meta description, plus a preview of the generated block where the page has one.
- **Publish:** confirmation showing the SHA-256 and "cannot be changed afterwards", then the effective time.
- **History:** every version, read-only, with publisher, time and change note.
- **Audit** (02 §15): `content.page_published`, family `configuration`, subject `cms_page`. It records `page_key`, `version_no`, `effective_from` and `body_sha256`, never the text. Draft saves are not audited; the version row is the record.
- **Local seeding:** placeholder text for all five pages, local only, never in production. This follows the placeholder terms seeder (02 §25.10).

### 2.5 Cookies (PECR)

- **Cookie registry** in code (`App\Domain\Cms\CookieRegistry`): name, set by (first or third party), purpose, lifetime and category. At launch every entry is `strictly_necessary`: `laravel_session`, `XSRF-TOKEN`, the guest cart session, `price_display` (05.15 §4.1), and Stripe's fraud-prevention cookies on the payment step (`__stripe_mid`, `__stripe_sid`).
- The Cookies page renders the registry as a table under the editable introduction.
- **Test that keeps it true:** a feature test walks the storefront pages, the cart, checkout and sign-in, collects every `Set-Cookie` name, and fails on any name missing from the registry. Adding a cookie without listing it breaks the build.
- **No consent banner** while every entry is strictly necessary (PECR reg. 6(4)). Adding any entry with another category is blocked until a consent-banner section of this document is signed off (05.15 §8.2). The registry rejects such an entry in production.

## 3. Schema (amendment to 02, signed off 2026-10-05; 02 §30)

```sql
CREATE TABLE cms_pages (
  id                        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  page_key                  text        NOT NULL,
  draft_title               text,
  draft_meta_description    text,
  draft_body_markdown       text,
  draft_updated_at          timestamptz,
  draft_updated_by_user_id  bigint      REFERENCES users (id),
  created_at                timestamptz NOT NULL DEFAULT now(),
  updated_at                timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT cms_pages_key_uq  UNIQUE (page_key),
  CONSTRAINT cms_pages_key_chk CHECK (page_key IN
    ('privacy','cookies','delivery','returns','contact')),
  CONSTRAINT cms_pages_draft_meta_chk CHECK (
    draft_meta_description IS NULL OR length(draft_meta_description) <= 320)
);

CREATE TABLE cms_page_versions (
  id                    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  cms_page_id           bigint      NOT NULL REFERENCES cms_pages (id),
  version_no            integer     NOT NULL,
  title                 text        NOT NULL,
  meta_description      text,
  body_markdown         text        NOT NULL,
  body_sha256           text        NOT NULL,
  effective_from        timestamptz NOT NULL,
  change_note           text,
  published_by_user_id  bigint      NOT NULL REFERENCES users (id),
  created_at            timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT cms_page_versions_no_uq        UNIQUE (cms_page_id, version_no),
  CONSTRAINT cms_page_versions_effective_uq UNIQUE (cms_page_id, effective_from),
  CONSTRAINT cms_page_versions_no_chk       CHECK (version_no >= 1),
  CONSTRAINT cms_page_versions_sha_chk      CHECK (body_sha256 ~ '^[0-9a-f]{64}$'),
  CONSTRAINT cms_page_versions_title_chk    CHECK (btrim(title) <> ''),
  CONSTRAINT cms_page_versions_meta_chk     CHECK (
    meta_description IS NULL OR length(meta_description) <= 320)
);

-- reject_row_mutation() exists (02 §25.1)
CREATE TRIGGER cms_page_versions_immutable
  BEFORE UPDATE OR DELETE ON cms_page_versions
  FOR EACH ROW EXECUTE FUNCTION reject_row_mutation();
```

- **The current version** is the row with the latest `effective_from <= now()` for a page. `cms_page_versions_effective_uq` serves it by a backward index scan, as `terms_versions_kind_effective_uq` does (02 §25.1). No extra index is needed.
- `version_no` is per page and taken under a `FOR UPDATE` lock on the `cms_pages` row, so it is gapless per page. It is a display number, not a document series, so it does not use `number_sequences`.
- **Caching:** the current version per page is cached until the next scheduled `effective_from` or until a publish, whichever comes first.
- **No new configuration keys.** Contact details and legal details come from the existing `brand.*` and `seller.*` keys.

## 4. Head tags, canonical and indexing rules

### 4.1 Rendered on the server

The app renders on the client (no Inertia SSR), and not every crawler runs JavaScript. So everything in this section is written into the **initial HTML** by `resources/views/app.blade.php`, Inertia's root template, from a `SeoHead` value object the controller passes as view data. React's `<Head>` keeps the title in sync during client-side navigation only. JSON is encoded with `JSON_HEX_TAG | JSON_HEX_AMP | JSON_HEX_APOS | JSON_HEX_QUOT | JSON_UNESCAPED_SLASHES`, so no catalogue text can close the `<script>` tag.

### 4.2 Indexing matrix

| Route | `robots` | Canonical |
|---|---|---|
| `/` | `index, follow` | `/` |
| `/c/{slug}` with no query string | `index, follow` | itself |
| `/c/{slug}` with any filter, sort or `after` parameter | `noindex, follow` | **none** (no conflicting signals) |
| `/p/{slug}` | `index, follow` | itself, query string removed |
| `/search` (any query) | `noindex, follow` | none |
| `/privacy`, `/cookies`, `/delivery`, `/returns`, `/contact`, `/terms` | `index, follow` | itself |
| Cart, checkout, account, `/orders/*`, sign-in, registration, password, 2FA, order pad, warehouse, `/admin` | `noindex, nofollow`, also sent as an `X-Robots-Tag` header | none |
| 403, 404, 410, 419, 500 | `noindex` | none |

- **Tracking parameters** (`utm_*`, `gclid`, `fbclid`, `msclkid`) do not count as filters. The page stays indexable with its clean canonical.
- **Canonical form:** absolute `https://` URL on `config('app.url')`'s host, lower-case slug, no trailing slash. A slug requested in another case gets a **301** to the lower-case form. (The routes accept `[A-Za-z0-9-]+` today.)
- **Hidden or archived category, inactive or deleted product:** 404. Whether a discontinued product should 301 to its category is Q3.
- **Not production, or indexing switched off** (§4.4): every response carries `X-Robots-Tag: noindex, nofollow`, and `robots.txt` disallows everything.

### 4.3 Titles, descriptions, social tags

- **Title:** `{meta_title or name} · {brand.name}`. The home page is `{brand.name}`, plus ` — {brand.tagline}` when a tagline is set.
- **Description:** `meta_description`, falling back to the product's `short_description` (or a category's own text), cut at 160 characters on a word boundary. Never cost, never a stock figure.
- **Open Graph:** `og:title`, `og:description`, `og:url` (the canonical), `og:image` (the product's first image, or the logo), and `og:type` (`product` or `website`).
- `<html lang="en-GB">` (currently `en`).

### 4.4 A switch before go-live

**`seo.indexing_enabled`**: global, `bool`, default **false**. It is a new `system_configurations` key, edited on the Storefront settings page and audited like the other storefront settings (05.15 §3.1). Until the business switches it on, the live site behaves like staging (§4.2 last bullet). This stops search engines indexing a store before the legal review (05.15 Q1) is done.

## 5. Structured data

JSON-LD in the initial HTML (§4.1). It is always computed **from a logged-out visitor's point of view**, whoever is viewing: rank-5 `base` prices (03 §4.2), GB VAT, inc VAT. So a signed-in trade viewer's own price never reaches a crawler-visible block. It never includes cost (invariant 9) or a stock figure.

### 5.1 `Product` (product page)

| Property | Source |
|---|---|
| `name`, `description`, `url`, `image[]` | Product name, short description, canonical URL, absolute image URLs (gallery order) |
| `brand` | `{"@type": "Brand", "name": …}` when set |
| `sku`, `gtin13` | Single-SKU product only: `sku_code`, and `barcode_ean` when it is a valid 13-digit EAN |
| `offers` | **One SKU:** an `Offer`. **Several:** an `AggregateOffer` with `lowPrice`, `highPrice` and `offerCount`, over active SKUs |
| `offers.price` | The gross "each" price the page shows: qty 1, `base` list, GB rate, `gross_e4 = roundHalfUpDiv(net_e4 × (10000 + rate_bp), 10000)`, shown to the penny (05.15 §4.3). Formatted from integers as `"12.34"`, never through a float |
| `offers.priceCurrency` | `GBP` |
| `offers.eligibleQuantity` | When the minimum purchase is above 1 (MOQ or the default pack): `{"@type": "QuantitativeValue", "minValue": <base qty>, "unitCode": "C62"}` |
| `offers.availability` | `in_stock` → `InStock`; `low_stock` → `LimitedAvailability`; `backorder` → `BackOrder`; `out_of_stock` → `OutOfStock` (labels per 05.15 §5.3, no figures) |
| `offers.itemCondition` | `NewCondition` |
| `offers.seller` | `{"@type": "Organization", "name": brand.name}` |
| `offers.hasMerchantReturnPolicy` | Public selling only: `applicableCountry: GB`, `returnPolicyCategory: MerchantReturnFiniteReturnWindow`, `merchantReturnDays: 14`, `returnMethod: ReturnByMail`, `returnFees: ReturnFeesCustomerResponsibility` (05.15 §7.2) |

- **`offers` is left out** when no `base` price resolves, or when `catalogue.guest_price_visibility = 'hidden'` (05.13 §14).
- No `shippingDetails` at launch. Rates depend on weight and zone, and a single figure would mislead (Q5).
- No `aggregateRating` (there are no reviews).

### 5.2 `BreadcrumbList` (category and product pages)

`Home → category path (CategoryPath) → current page`. Each `ListItem` has `position`, `name` and `item` (an absolute canonical URL). It matches the desktop breadcrumb the page shows.

### 5.3 `Organization` (home page only)

`name` (`brand.name`), `legalName` (`seller.legal_name`), `url`, `logo` (an absolute URL of `brand.logo_path`, when set), `vatID` (`seller.vat_number`), `address` (`seller.address`), and `contactPoint` (`brand.support_phone`/`support_email`, `contactType: customer service`, `areaServed: GB`). No `SearchAction`: Google retired the sitelinks search box in 2024.

### 5.4 Validation

A feature test parses the JSON-LD of a fixture product with one SKU, one with several SKUs, a zero-rated SKU and a product with no price. It asserts the price string equals the page's displayed gross price, that no `cost` key or stock figure appears, and that `offers` is absent when prices are hidden. The JSON is also checked against a stored schema.org shape snapshot.

## 6. `/sitemap.xml` and `robots.txt`

### 6.1 Sitemap

- `GET /sitemap.xml`, `application/xml`, served only when indexing is on (§4.4). Otherwise it returns 404.
- **URLs:** `/`; every `active` category; every product with `status = 'active'`, `published_at <= now()`, `deleted_at IS NULL` and at least one active SKU; every page in §2.1 that has a current version; and `/terms` when a `sale` version is in force.
- `lastmod` = the row's `updated_at` (for a page, its version's `effective_from`). No `changefreq` or `priority`, which Google ignores.
- **Generated on request** by a keyset walk over `products_active_published_idx` (02 §5.4). It is streamed, cached for 1 hour, and the cache is dropped when a product, category or page publishes or unpublishes.
- **Over 50,000 URLs or 50 MB:** `/sitemap.xml` becomes a sitemap index over `/sitemaps/products-{n}.xml` pages of 50,000 each. At ~920 SKUs this won't happen soon, but the code handles it so nothing changes at the limit.

### 6.2 `robots.txt`

Served by a route, not the static `public/robots.txt`. The static file is deleted, because the web server would serve it first and the response must vary by environment.

```
# production, indexing on
User-agent: *
Disallow: /admin
Disallow: /cart
Disallow: /checkout
Disallow: /account
Disallow: /orders/
Disallow: /order-pad
Disallow: /warehouse
Disallow: /api/
Sitemap: https://{host}/sitemap.xml

# anything else
User-agent: *
Disallow: /
```

`/search` and filtered category pages are **not** disallowed. A crawler must be able to fetch them to see their `noindex`.
