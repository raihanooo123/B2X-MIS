## 1. Purpose

Two capabilities that share nothing technically but both concern **acting on someone else's behalf**:

- **Part A — Dropship.** Shipping direct to the trade customer's own end customer, with no sign of us in the parcel.
- **Part B — Rep tools.** Staff ordering, quoting and managing accounts on a customer's behalf, with commission attached.

They are one document because both raise the same two questions — whose data is this, and who is accountable for the action — and both answer them the same way: snapshot the third party's data rather than accumulating it, and record the acting party on every transaction.

---

## 2. What the reference system gets wrong

Dropship is offered as a service and handled by arrangement. Rep tooling does not exist; phone orders are keyed by staff into the customer's own account with no record of who did it.

| Reference system | Consequence | Requirement here |
|---|---|---|
| Dropship by email arrangement | Every order is manual; no rating, no tracking | First-class `fulfilment_type` with its own document set |
| No blind documentation | Our invoice or pricing reaches the end customer | Blind packing note; pricing never leaves the building |
| End-customer addresses kept ad hoc | We accumulate our customers' customer lists | Snapshot-only in `order_addresses`; never in `addresses` |
| Phone orders keyed as the customer | No record of who placed it | `placed_by_user_id` distinct from `user_id`, always |
| No rep customer book | Accounts unowned; lapses unnoticed | Assigned book with lapse detection |
| No commission | Incentive managed on spreadsheets | Computed from margin at invoice, clawed back on return |
| No activity record | Visit and call history lives in individual inboxes | `customer_activities` timeline |

## 4. `dropship_profiles`

```sql
CREATE TABLE dropship_profiles (
  id                   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  company_id           bigint      NOT NULL REFERENCES companies (id) ON DELETE CASCADE,
  sender_name          text        NOT NULL,
  sender_phone         text,
  sender_email         citext,
  return_address       jsonb       NOT NULL,
  logo_media_id        bigint      REFERENCES media (id),
  note_template        text,
  include_prices       boolean     NOT NULL DEFAULT false,
  carriage_recharge_bp smallint,
  status               text        NOT NULL DEFAULT 'pending_approval',
  approved_by_user_id  bigint      REFERENCES users (id),
  approved_at          timestamptz,
  created_at           timestamptz NOT NULL DEFAULT now(),
  updated_at           timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT dropship_profiles_company_uq UNIQUE (company_id),
  CONSTRAINT dropship_profiles_status_chk CHECK (status IN
    ('pending_approval','active','suspended')),
  CONSTRAINT dropship_profiles_recharge_chk
    CHECK (carriage_recharge_bp IS NULL OR carriage_recharge_bp <= 10000),
  CONSTRAINT dropship_profiles_approved_chk
    CHECK (status <> 'active' OR approved_by_user_id IS NOT NULL)
);

CREATE INDEX dropship_profiles_status_idx ON dropship_profiles (status);
```

- `UNIQUE (company_id)` — one profile per account. Multiple sender identities per account would be a reseller running several brands, which is out of scope at launch and additive later.
- `include_prices` defaults to **0**. The safe default is that no price reaches the end customer; a trade customer who wants their own retail prices shown opts in.
- `status = 'pending_approval'` on creation. Dropship is a service with a cost, granted rather than self-served.
- `carriage_recharge_bp` optionally uplifts the carriage charged to the trade customer above the rated cost, which is how a distributor prices the service.

## 5. Order flow

### 5.1 Placement

`orders.fulfilment_type = 'dropship'` (02 §8.2), with:

- **Delivery address is the end customer's**, captured per order and snapshotted into `order_addresses` (02 §4.5, §8.4). Type `delivery`.
- **Billing address remains the trade customer's.** The trade customer pays; the end customer receives. Two different parties on one order, which is exactly what `order_addresses` already models.
- Carriage rated to the end customer's postcode (05.6 §4), charged to the trade customer, optionally uplifted by `carriage_recharge_bp`.
- `orders.channel = 'dropship'`, so volume and cost per account are reportable.

### 5.2 One order, one destination

**A dropship order ships to exactly one destination.** Several destinations means several orders.

This is a deliberate constraint, not a limitation. Allocation, shipment, carriage rating, tracking and partial dispatch are all specified per order in Docs 04, 05.5 and 05.6. Permitting several destinations per order would require every one of those to become per-destination, which is a substantial redesign to avoid a batch-upload feature that §5.4 provides instead.

### 5.3 Privacy by design

End-customer addresses are stored **only** as snapshots in `order_addresses`. They are never written to `addresses`, never attached to a `companies` row, and never aggregated into a reusable address book.

The reason is not schema tidiness. These are **third parties' personal data, belonging to our customer's relationship, not ours.** Accumulating a queryable database of our customers' customers creates a GDPR obligation we have no lawful basis for and no business need to hold. Snapshot-only means:

- The data exists solely as part of a transaction record, retained under the order retention policy
- There is no "all end customers" query, because there is no table to run it against
- A trade customer's data-deletion request is satisfied by the order retention policy, not by unpicking a separate store

Doc 07 covers retention periods. The relevant point here is that the constraint is enforced by **not having the table**, which is stronger than a policy about how to use one.

### 5.4 Batch upload

A CSV creating many single-destination orders in one action:

```
end_customer_name, address_1, address_2, city, postcode, country, sku_code, quantity, reference
```

Processed on a queue with a reconciliation screen before anything is committed, following the same pattern as the order pad's paste and CSV flows (05.1 §7):

| Outcome | Presentation |
|---|---|
| Valid | Destination, items, rated carriage, order total |
| Unrateable postcode | Listed; manual quote or correction |
| SKU not found or inactive | Listed with the input row |
| Quantity adjusted by MOQ or increment | Highlighted with the reason |
| Insufficient stock across the batch | Listed; the batch is allocated in file order, and the shortfall is named |

Nothing is created until confirmed. Partial confirmation is permitted. **Credit is checked against the batch total, not per order** — a hundred £40 orders is a £4,000 exposure, and checking each in isolation would pass a customer straight through their limit.

### 5.5 Documentation

| Document | Goes to | Contains |
|---|---|---|
| Blind packing note | In the parcel | Trade customer's branding and sender name, end-customer address, items and quantities. **No prices, no our-branding, no our-contact-details** |
| Courier label | On the parcel | Sender per `dropship_profiles.return_address_json` |
| Invoice | Trade customer, by email | Normal invoice, never in the parcel |
| Tracking notification | Trade customer | Per destination, forwardable to their customer |

Enforced at generation, not by template discipline: the dropship packing note is a **distinct document type** with no price fields in its data payload at all. A template cannot accidentally render what was never passed to it — the same reasoning as cost figures being absent from customer-facing payloads (03 §11).

The pick and pack screens show a prominent blind-shipment marker (05.5 §7.1) so nothing is added to the box by habit.

### 5.6 Returns

Goods return from the **end customer**, but the commercial relationship is with the trade customer.

- The RMA is raised by the trade customer (05.4 §7.1), who states what the end customer is returning.
- Return goods arrive at our warehouse from a third-party address; the RMA number on the parcel is what attributes it.
- Fee, refund and credit note all settle against the trade customer, per 05.4 §6.
- An end customer contacting us directly is redirected to the trade customer. We have no relationship with them and no basis to act on their instruction.

## 7. Customer book

`companies.assigned_rep_user_id` (02 §4.3) with `companies_rep_idx`. A rep's book is every company assigned to them.

The rep dashboard surfaces, per account: last order date, order value trend, open quotes with expiry, credit position and any overdue invoice, open RMAs, and last recorded activity.

### 7.1 Lapse detection

```
lapsed when  days_since_last_order > (median_order_interval × configured_multiplier)
             OR days_since_last_order > configured_absolute_days
```

Median rather than mean, because a single unusual gap should not reset the baseline for an otherwise regular account. A customer ordering every three weeks is lapsed at six; one ordering quarterly is not.

Accounts with fewer than three orders fall back to the absolute threshold — there is no interval to compute.

## 8. Order-on-behalf

Specified in 05.1 §8.4 for the order pad. The rules, stated once and applying everywhere:

| Rule | Detail |
|---|---|
| Explicit selection | A rep chooses an account from their book. No implicit context |
| Unmistakable banner | Whose account is active, persistently visible, on every screen |
| Real prices | The customer's actual tier, contract and promotion pricing. Never a rep-only price list |
| Dual attribution | `orders.user_id` = the customer contact if named, `placed_by_user_id` = the rep, `sales_rep_user_id` = the owning rep. All three always written |
| Same rules | Every credit, MOQ, minimum-order and stock rule applies identically |
| No override of control | A rep **cannot** raise a credit limit, lift a suspension, approve their own quote, or bypass a credit block. They can request; someone else decides |
| Audited | Session start, account, and every action written to the audit log |

The last two matter most. **A rep placing an order for a suspended account is blocked on the same rules as the customer** (05.2 §12). The ability to act on someone's behalf must not become a route around the controls that exist to protect the business from that same account.

## 9. `customer_activities`

```sql
CREATE TABLE customer_activities (
  id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  company_id    bigint      NOT NULL REFERENCES companies (id) ON DELETE CASCADE,
  user_id       bigint      NOT NULL REFERENCES users (id),
  activity_type text        NOT NULL,
  subject       text,
  body          text,
  outcome       text,
  follow_up_on  date,
  related_type  text,
  related_id    bigint,
  occurred_at   timestamptz NOT NULL DEFAULT now(),
  created_at    timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT customer_activities_type_chk CHECK (activity_type IN
    ('call','visit','email','note','quote_sent','order_placed',
     'complaint','credit_discussion','sample_sent')),
  CONSTRAINT customer_activities_outcome_chk CHECK (outcome IS NULL
    OR outcome IN ('positive','neutral','negative','no_contact'))
);

CREATE INDEX customer_activities_company_idx
  ON customer_activities (company_id, occurred_at DESC, id);
CREATE INDEX customer_activities_user_idx
  ON customer_activities (user_id, occurred_at DESC);
-- partial: a rep's daily list only wants outstanding follow-ups
CREATE INDEX customer_activities_follow_up_idx
  ON customer_activities (follow_up_on, user_id)
  WHERE follow_up_on IS NOT NULL;
CREATE INDEX customer_activities_related_idx
  ON customer_activities (related_type, related_id) WHERE related_type IS NOT NULL;
CREATE INDEX customer_activities_body_trgm
  ON customer_activities USING gin (body gin_trgm_ops) WHERE body IS NOT NULL;
```

- System events (`quote_sent`, `order_placed`) are written automatically, so the timeline is complete without depending on a rep remembering.
- `customer_activities_follow_up_idx (follow_up_on, user_id)` drives each rep's daily follow-up list.
- Activities are **append-only by convention**: no `updated_at`, and corrections are new entries. A note recording what a customer said should not be editable after the fact.

## 10. Commission

### 10.1 Rules

```sql
CREATE TABLE rep_commission_rules (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id     bigint    NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  category_id bigint    REFERENCES categories (id),
  basis       text      NOT NULL DEFAULT 'net_margin',
  rate_bp     smallint  NOT NULL,
  validity    tstzrange NOT NULL DEFAULT tstzrange(now(), NULL, '[)'),
  created_at  timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT rep_commission_rules_basis_chk
    CHECK (basis IN ('net_margin','net_revenue')),
  CONSTRAINT rep_commission_rules_rate_chk CHECK (rate_bp <= 10000),
  CONSTRAINT rep_commission_rules_validity_chk CHECK (NOT isempty(validity)),
  -- one live rate per rep per category; NULL category = the rep default.
  -- category_id is nullable, and gist EXCLUDE never matches two NULLs
  -- (NULL = NULL is unknown, not true), so two overlapping "rep default"
  -- rows for the same user_id would both insert cleanly without this.
  -- COALESCE collapses NULL to a real, comparable value so the default
  -- case is compared like any other category. Correction 2026-09-22,
  -- same class of bug as tax_rates_no_overlap (02 §6.2) and
  -- order_spend_breaks_no_overlap (02 §6.7).
  CONSTRAINT rep_commission_rules_no_overlap
    EXCLUDE USING gist (user_id WITH =, COALESCE(category_id, 0) WITH =, validity WITH &&)
);

CREATE INDEX rep_commission_rules_resolve_idx
  ON rep_commission_rules (user_id, category_id)
  INCLUDE (basis, rate_bp, validity);
```

`category_id` NULL is the rep's default rate. Resolution is **most specific wins, walking up the category tree** — the identical pattern and identical query shape as discount authority (05.3 §6.3), using `category_closure_descendant_idx`. A rate set on "Kitchen" applies to every descendant category.

### 10.2 ⚠️ Closes Doc 02 §13 Q3 — commission is on net margin

**Basis defaults to `net_margin`**, not net revenue.

Revenue-based commission rewards a rep for conceding price: a deeper discount closes the order and pays the same percentage on a smaller number, so the rep's incentive and the business's diverge exactly where it matters. Margin-based commission aligns them — and the system already has what it needs, because `order_lines.unit_cost_e4` is snapshotted at placement (02 §8.3) and made real by landed cost (05.7 §8).

This is only possible because landed cost is computed. Commission on FOB-based margin would pay out on a margin that does not exist (05.7 §8.3: a 42p grater actually costs 52.4p).

`net_revenue` remains available per rep per category, because some product lines are sold on volume and the simpler basis is defensible there.

### 10.3 `rep_commissions`

```sql
CREATE TABLE rep_commissions (
  id                 bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id            bigint      NOT NULL REFERENCES users (id),
  company_id         bigint      NOT NULL REFERENCES companies (id),
  order_id           bigint      NOT NULL REFERENCES orders (id),
  order_line_id      bigint      REFERENCES order_lines (id),
  invoice_id         bigint      REFERENCES invoices (id),
  rma_id             bigint      REFERENCES rmas (id),
  basis              text        NOT NULL,
  basis_amount_minor bigint      NOT NULL,
  rate_bp            smallint    NOT NULL,
  amount_minor       bigint      NOT NULL,
  period_key         char(7)     NOT NULL,
  status             text        NOT NULL DEFAULT 'accrued',
  clawback_of_id     bigint      REFERENCES rep_commissions (id),
  accrued_at         timestamptz NOT NULL DEFAULT now(),
  paid_at            timestamptz,
  note               text,

  CONSTRAINT rep_commissions_accrual_uq
    UNIQUE NULLS NOT DISTINCT (order_line_id, invoice_id, clawback_of_id),
  CONSTRAINT rep_commissions_basis_chk CHECK (basis IN ('net_margin','net_revenue')),
  CONSTRAINT rep_commissions_status_chk CHECK (status IN
    ('accrued','payable','paid','clawed_back','cancelled')),
  CONSTRAINT rep_commissions_rate_chk CHECK (rate_bp <= 10000),
  -- a clawback is a negative row, never an edit
  CONSTRAINT rep_commissions_sign_chk
    CHECK ((clawback_of_id IS NULL AND amount_minor >= 0)
        OR (clawback_of_id IS NOT NULL AND amount_minor < 0))
);

CREATE INDEX rep_commissions_user_period_idx
  ON rep_commissions (user_id, period_key, status) INCLUDE (amount_minor);
-- partial: the payment run only looks at what is not yet paid
CREATE INDEX rep_commissions_payable_idx ON rep_commissions (accrued_at)
  WHERE status IN ('accrued','payable');
CREATE INDEX rep_commissions_order_idx ON rep_commissions (order_id);
CREATE INDEX rep_commissions_clawback_idx ON rep_commissions (clawback_of_id)
  WHERE clawback_of_id IS NOT NULL;
```

- `rep_commissions_accrual_uq` makes accrual idempotent — a retried invoicing job cannot pay commission twice. The same guarantee as `credit_holds_order_uq`, `quotes_converted_order_uq` and `collection_bookings_order_uq`.
- `period_key` is `YYYY-MM`, so `rep_commissions_user_period_idx` gives a rep's statement as one covering range.
- Commission is **signed**: a clawback is a negative row referencing the original via `clawback_of_id`, never an edit or deletion. The same append-only correction discipline as the stock and account-credit ledgers.

### 10.4 Lifecycle

| Event | Effect |
|---|---|
| Order invoiced | `accrued` rows written per **goods line**, from the snapshotted margin |
| Invoice paid in full | Rows move to `payable` |
| Invoice unpaid past a configured threshold | Held at `accrued`; not payable |
| Credit note from a return | Negative row at `clawed_back`, referencing the original |
| Order cancelled before invoicing | Rows `cancelled` |
| Period closed and paid | Rows `paid` with `paid_at` |

**Commission becomes payable on payment, not on dispatch.** A rep is not paid for an order the business was never paid for — and on 30-day terms with credit accounts, the gap between the two is where the risk lives.

### 10.4a Basis excludes carriage and fees

**Commission accrues on goods lines only.** `orders.shipping_net_minor`, restocking fees (05.4 §6.2), carriage recharges (05.8 §4) and cancellation charges are all excluded from `basis_amount_minor`.

Carriage is a pass-through cost recovery, not a sale — paying commission on it rewards a rep for a distant delivery address. A restocking fee is compensation for handling a return, and paying commission on it would reward the rep for the return itself.

The consequence for clawbacks is specific and worth stating: when goods are returned and a £74.30 restocking fee is retained, **commission on the returned goods is clawed back in full, and the retained fee generates none.** The rep neither keeps commission on the reversed sale nor earns on the penalty.

### 10.4b Self-service orders accrue to the assigned rep

An order a customer places themselves, on an account with an assigned rep, **accrues commission to that rep.**

Accrual keys on `orders.sales_rep_user_id`, not `placed_by_user_id`. The two differ precisely in this case: `placed_by_user_id` is NULL or the customer's own user, while `sales_rep_user_id` carries the owning rep.

The rationale is that the rep built and maintains the account. Paying only on rep-keyed orders would create an incentive against the self-service order pad — the rep would be rewarded for keeping customers on the telephone, which is the opposite of what this platform is for.

`sales_rep_user_id` is **stamped at placement** from `companies.assigned_rep_user_id`, so reassigning the account later never moves historical commission.

### 10.5 Statement

Per rep per period: accrued, payable, paid, clawed back, net. Drilling to order and line, showing basis amount and rate. Reps see their own; managers see the team.

Cost and margin figures are visible here because reps are an authorised context (03 §11). Reps must **not** see cost on any customer-facing surface, including a screen they are sharing on a call.

## 12. Edge cases

| Case | Behaviour |
|---|---|
| Dropship batch of 100 orders, credit sufficient for 60 | Batch allocated in file order; shortfall named. Nothing committed until confirmed |
| End-customer postcode unrateable | That destination goes to manual quote; the rest of the batch proceeds |
| End customer contacts us directly | Redirected to the trade customer. No relationship, no basis to act |
| Trade customer asks for all past end-customer addresses | Available only within their own order records. There is no separate store, by design |
| Dropship profile suspended mid-order | Existing orders complete; no new dropship orders accepted |
| Rep leaves; accounts and open quotes remain | Reassignment moves the book and quote ownership; historical attribution unchanged |
| Rep reassigned mid-period | Commission follows `orders.sales_rep_user_id` stamped at placement, not the current assignment |
| Customer self-serves on an assigned account | Commission accrues to the assigned rep (§10.4b) |
| Order on an account with no assigned rep | No commission accrues; no orphan rows written |
| Order margin negative after landed cost finalisation | Commission accrues on the snapshotted figure; the variance is reported, not retro-charged |
| Invoice part-paid | Commission payable pro rata to the paid proportion |
| Return after commission paid | Negative clawback row; recovered against the next period |
| Rep tries to place an order for a suspended account | Blocked on the same rules as the customer |
| Rep shares their screen with a customer on a call | Cost is visible on rep surfaces. Flagged as a training matter in Doc 07, not solvable in schema |

## 13. Test matrix

**Dropship:** blind packing note payload contains no price field at all, verified by inspecting the data passed to the template, not the rendered output · no invoice is generated into the parcel document set · carriage rated on the end-customer postcode and charged to the trade customer · `carriage_recharge_bp` uplift applied correctly · end-customer address written to `order_addresses` and **never** to `addresses`, asserted by query-log inspection · batch upload reconciliation classifies every row outcome · batch credit checked against the total, not per order · a dropship order cannot be created with two delivery destinations.

**Order-on-behalf:** all three of `user_id`, `placed_by_user_id` and `sales_rep_user_id` written on every rep order · rep cannot raise a credit limit, lift a suspension, or approve their own quote · rep order for a suspended account blocked identically to the customer's own attempt · banner present on every screen of a rep session.

**Commission:** basis excludes carriage, restocking fees and cancellation charges, asserted per field · a self-service order on an assigned account accrues to that rep · an order with no assigned rep accrues nothing · a return retaining a restocking fee claws back goods commission in full and earns none on the fee · rate resolution prefers explicit category over ancestor over rep default · ancestor rate on "Kitchen" applies to descendants · accrual idempotent under a retried invoicing job, verified by `rep_commissions_accrual_uq` · commission payable only on payment · part-payment accrues pro rata · credit note produces a negative clawback row, never an edit · `Σ commission rows` for a period equals the statement net, exactly · margin basis computes from the snapshotted `unit_cost_e4`, not from current cost.

**Property:** for any sequence of invoice, part-payment, return and clawback events, a rep's net commission equals the sum of their signed rows, with no row ever updated or deleted.

## 14. Acceptance criteria

1. A blind packing note carries no price data in its payload, and no invoice is producible into a parcel.
2. End-customer addresses exist only as `order_addresses` snapshots; no code path writes them to `addresses`.
3. A dropship order has exactly one destination; multi-destination fulfilment is achieved by batch upload creating separate orders.
4. Batch upload checks credit against the batch total and commits nothing before confirmation.
5. Every rep-placed order records all three user references.
6. A rep cannot bypass or alter any credit, suspension or approval control, verified per control.
7. Commission accrues on net margin of **goods lines only**, from snapshotted cost, becomes payable only on payment, and is idempotent under retry.
7a. Self-service orders on an assigned account accrue to that rep, keyed on `sales_rep_user_id` stamped at placement.
8. Returns produce negative clawback rows; no commission row is ever updated or deleted.
9. Commission rate resolution walks the category tree with the same semantics as discount authority.
10. Lapse detection uses median order interval, with an absolute fallback for accounts with fewer than three orders.
