## 1. Purpose

Who can sign in, how they get an account, and what each kind of visitor can do before and after. This spec covers the **flows**; 07 §6.1 already fixes the **policy** (password hashing, 2FA scope, session timeouts, rate limits, reset-token lifetime) and nothing here relaxes it.

The flows are B2B-specific in ways a stock login kit does not handle:

- A trade account is a **company** with several users, not a person (05.2 §10).
- An applicant exists before their company is approved (05.2 §4), and the pricing engine treats them as unapproved until it is (03 §4.2 rank 5).
- A buyer builds a cart before signing in, and it must survive login (02 §14.3).
- Staff and customers share one `users` table but not one security posture (07 §6.1, 02 §14.1).

## 2. What the reference system gets wrong

| Reference system | Consequence | Requirement here |
|---|---|---|
| "B2B Registration" is a second signup form at a different URL (05.2 §2) | Two account types that never meet; trade status is a label, not a state | One account, one application flow, trade status derived from an approved company |
| One login per business, shared (05.2 §2) | No audit of who ordered; ex-staff keep access | Individual users on a company account, invited by its owner |
| Registration grants immediate buying | No vetting | Applicant signs in, sees status and base prices, cannot check out until approved (05.2 §5.3) |
| Basket lost or duplicated on login | Buyers re-key orders | Guest cart merged on login, deterministically (§8) |
| No second factor anywhere | Staff credentials alone reach pricing, credit and stock | 2FA mandatory for every staff role (07 §6.1) |

| # | As a… | I want to… | So that… |
|---|---|---|---|
| U1 | prospective trade buyer | apply and create my login in one step | I don't fill in two forms |
| U2 | applicant | sign in and see where my application stands | I'm not left guessing (05.2 U2) |
| U3 | applicant | browse the catalogue at base prices while I wait | I can plan my first order |

## 4. Identities and their states

### 4.1 Who signs in

Everyone who authenticates is a `users` row (02 §4.2). What they may do is **derived**, never stored as a user "type":

| Identity | How it is recognised | Prices seen | Can check out |
|---|---|---|---|
| Guest | No session user | Per §14 | No — must sign in (§14) |
| Applicant | Signed-in user with an **open** `b2b_applications` row (`status` in `submitted`, `in_review`, `info_requested`) where `applicant_user_id` = the user, and no `company_users` row | Base (05.2 §5.3) | **No** — 05.2 §5.3 |
| Trade user | Signed-in user with a `company_users` row on a company whose `status = 'approved'` | Company's tier and contract prices (03 §4.2) | Per `company_users.role` and the company's credit state (05.2 §9–10) |
| Public customer | Signed-in user with no `company_users` row and no open application (01 §4) | Base | Card or prepay only, no credit check or hold (`ConsumerCheckout`), once their email is verified (§11) |
| Staff | Signed-in user with one or more `role_user` rows (02 §14.1) | n/a in the admin panel; staff acting for a customer use 05.8's order-on-behalf session | Only on behalf of a customer (05.1 §8.4, 05.8) |

The same person can hold more than one identity: a staff member can also be a `company_users` member, and a user can belong to several companies (02 §4.4). Where postures conflict, the **stricter** applies. A user holding any staff role gets staff 2FA (§12) and staff session limits (§13) in every context.

### 4.2 `users.status`

02 §4.2 defines the values but not what they mean. This spec defines them:

| Status | Meaning | Can sign in |
|---|---|---|
| `pending` | A **staff** user created by an administrator who has not yet set a password (§5.3). `password_hash` is NULL. Trade and public users are never `pending`: company invitees have no `users` row until they accept (§9), and self-registration creates `active` users | No — only the onboarding link (§5.3) |
| `active` | Normal | Yes |
| `suspended` | Blocked by an administrator (per user, not per company) | No. Existing sessions end at once (§13.3) |
| `closed` | Account closed at the user's or business's request; erasure per 07 §7.3 | No |

Self-registration (§5.1, §5.2) creates the user as `active`, with `email_verified_at` NULL until verified (§11).

**User suspension is distinct from company suspension.** A company suspended for overdue debt (05.2 §9) blocks on-account checkout only. Its users can still sign in, see their invoices and pay by card. Suspending a *user* blocks sign-in.

### 4.3 Company role inside an account

`company_users.role` (`owner`, `buyer`, `approver`, `viewer`) governs what a trade user may do once signed in (05.2 §10). It plays no part in authentication, except that only an `owner` can invite (§9).

## 5. Registration

### 5.1 Trade buyers — apply and register in one step

The 05.2 §5.1 application form **is** the registration form. For a visitor who is not signed in, it adds three fields: **password**, password confirmation, and acceptance of the terms of trade.

On submit, in one transaction:

```
1. Validate the application (05.2 §5.1) and the password (§5.4)
2. Create users (status = 'active', email = contact email, email_verified_at NULL)
3. Create b2b_applications (status = 'submitted', applicant_user_id = the new user)
4. Duplicate checks per 05.2 §5.2
COMMIT
AFTER COMMIT: verification email (§11); "application received" email (05.2 §11)
              — the user is NOT signed in; see below
```

**Not signed in on registration** (amended 2026-09-24, at implementation). The first draft signed a new registrant straight in. That contradicts the no-enumeration rule below: an address with an existing account cannot be signed in (the visitor does not hold its password), so signing *new* registrants in would reveal which case each one was. Every registration therefore ends on the same "check your inbox, then sign in" confirmation. The guest cart merges at that first sign-in (§8), as for anyone.

A signed-in user who is not yet a trade user — a public customer, or a previously rejected applicant after the cooling period (05.2 §5.7) — applies through the same form **without** the password fields. The application links to their existing user.

**Existing email.** If the contact email already belongs to a user, the form does not say so on screen, because that would tell anyone which addresses have accounts. It shows the normal "check your inbox" confirmation. The email then tells the owner of that address they already have an account and gives a sign-in link, from which they can apply. No application is created until they are signed in.

**What approval changes.** 05.2 §5.6 step 4 says "Create **or link** the users row". Under this flow the user always exists already, so approval **links**: it inserts `company_users` with `role = 'owner'` for the `applicant_user_id`. The "create" branch remains only for applications a member of staff enters on a customer's behalf. Those carry `applicant_user_id = NULL`, and approval issues a `company_invitations` row (§9) with `role = 'owner'` to the contact email instead of creating a user.

### 5.2 Public customers

The platform sells to the public (01 §4, CLAUDE.md; decided 2026-09-24). A public customer is a user with no company: they buy at `base` prices (03 §4.2 rank 5), card or prepay only, with no credit check or hold (`ConsumerCheckout`), and none of the trade machinery — no tier, contract, credit or colleagues.

Registration is a separate, short form: first name, last name, email, password, confirmation, acceptance of the terms of sale.

```
1. Validate (password per §5.4)
2. Create users (status = 'active', email_verified_at NULL) — no company, no application
COMMIT
AFTER COMMIT: verification email (§11) — not signed in (§5.1)
```

The same no-enumeration rule as §5.1 applies to an existing email. A public customer can apply for a trade account at any time (§5.1, signed-in variant); while the application is open they are an **applicant** (§4.1), so their checkout is blocked as 05.2 §5.3 requires, and they return to public-customer buying if it is rejected or withdrawn (§7).

Public customers bring statutory consumer obligations the trade flows do not: the distance-selling cancellation right and VAT-inclusive price display. They are recorded in 07 §12 and **not yet specified** (07 §16 Q10). They concern returns (05.4) and price display (05.1, 03 §10), not authentication, and do not block anything in this document.

### 5.3 Staff

Staff do not self-register, and are not invited through `company_invitations` — staff have no company (02 §14.1, §17.1). An administrator creates the user (`status = 'pending'`, `password_hash` NULL) and grants roles (`role_user.granted_by_user_id`). The user receives a **set-your-password link issued by the password-reset broker** (§10, 02 §17.3), and so inherits its 60-minute expiry and single use; an administrator re-sends it if it lapses (⚑16). Setting the password makes the user `active` and verifies their email. Their first sign-in forces 2FA enrolment (§12.1) before any admin page loads.

### 5.4 Password rules

07 §6.1, applied wherever a password is set (§5.1, §5.2, §5.3, §9, §10): hashed with **Argon2id** (`config/hashing.php`; existing bcrypt hashes are rehashed at each user's next sign-in), at least **12 characters**, no composition rules, no forced rotation, and **not on the breached-password list**.

The breached-password check is **offline** (decided 2026-09-24): the submitted password is checked against a list held on the server, with **no network call** — so no password-derived data leaves the platform and no processor is added under 07 §7.5. Laravel's `Password::uncompromised()` rule calls an online API and is therefore **not** used; a local rule (`NotBreachedPassword`) replaces it.

**The list** (decided 2026-09-24, §19 Q17): Have I Been Pwned's SHA-1 list, held as HIBP's own range files — one file per 5-hex-digit SHA-1 prefix, `SUFFIX:COUNT` lines — under `storage/app/breached-passwords` (`BREACHED_PASSWORDS_PATH`). A check hashes the password, opens the one file for its prefix and scans it; nothing leaves the server.

- **Refreshed quarterly** by `auth:refresh-breached-passwords`, scheduled in `routes/console.php`. The refresh is the only contact with HIBP and sends nothing password-derived: it downloads all 16⁵ public ranges (~1 M requests, tens of GB on disk, hours to run), builds the new list beside the live one, and swaps it in only when every range arrived — a failed refresh leaves the previous list in use.
- **If the list is missing, the check fails open** — the password is accepted and a `critical` log entry is written. Refusing every new password would stop registration, resets and onboarding outright; a missing list is an operational fault to alert on (07 §9.3). The list must be populated before go-live (ROADMAP §16).

## 6. Sign-in

### 6.1 Flow

Authentication uses **Laravel Sanctum**'s first-party model (06 §1, CLAUDE.md approved stack): the session cookie plus CSRF, on the `web` guard. The Inertia app and the admin panel are same-origin, so the `/api/v1` calls the pad makes are authenticated by that same session through Sanctum's stateful middleware — there are no API tokens for first-party clients.

Two entry points share the `users` table and the guard:

| Entry | Route | Who |
|---|---|---|
| Storefront | `/login` (Inertia page) | Applicants, trade users, public customers |
| Admin panel | **None of its own** — staff sign in at `/login`; an unauthenticated `/admin` request is sent there and returned afterwards | Staff. `User::canAccessPanel()` gates the panel through the `accessAdminPanel` policy (CLAUDE.md: same Policies as everything else) |

**One sign-in page** (amended 2026-09-24, at implementation). The first draft kept FilamentPHP's own `/admin/login`. That page would bypass the lockout (§6.2) and the 2FA challenge (§12), so it is switched off; the panel's middleware still applies staff session limits and mandatory 2FA (§12.1, §13).

```
1. Lockout check (§6.2) — refused before any credential is examined
2. Look up by email (citext, users_email_uq — deleted rows excluded)
3. Verify the password. On failure, record it (§6.2) and show one generic message:
   "Those details don't match an account." — never "no such email"
4. status ≠ 'active' → the same generic message (a pending, suspended or closed
   account is not revealed)
5. If 2FA is required or enabled → challenge (§12) before the session is authenticated;
   a failed code is recorded as a failure (§6.2)
6. Regenerate the session id; set users.last_login_at; start the session clocks (§13)
7. Login event; audit (§15); clear this identifier's failure count (§6.2)
8. Company choice (§6.3) if the user belongs to more than one approved company
9. Guest cart merge (§8), into the cart of the identity chosen at step 8
10. Redirect: staff at /admin/login → panel; everyone else → the page they came
    from, else the order pad
```

Laravel's `Login` event fires only at step 7, after the second factor. A user who passes the password but abandons the 2FA challenge has not signed in, so their guest cart is not merged.

### 6.2 Rate limiting and lockout

Decided 2026-09-24. Failed attempts are counted **per IP and per identifier** (the submitted email, lower-cased), **independently**, and a lockout on either refuses the attempt:

| Consecutive failures on a counter | Lockout |
|---|---|
| 5 | 1 minute |
| 10 | 5 minutes |
| 15, and every further failure | 30 minutes |

- **Counters live in the cache, not the database** — nothing is persisted, and a counter disappears with its cache entry. No table is added (02 §17.5). The cache is Redis (`config/cache.php`, decided 2026-09-24, §19 Q18).
- **15-minute sliding window** (decided 2026-09-24, §19 Q18): each failure resets its counter's lifetime to 15 minutes, so a counter lapses 15 minutes after the *last* failure. One consequence, accepted: a 30-minute lockout outlasts the window, so once it ends the counter has already lapsed and the ladder starts again from 1.
- **Never permanent.** The ceiling is 30 minutes, so an attacker who knows a customer's email can delay but never lock them out indefinitely, and no lockout needs a human to lift.
- **Unknown identifiers are counted exactly like known ones**, so a lockout reveals nothing about whether an account exists.
- **A successful sign-in clears the identifier's counter, not the IP's** — otherwise an attacker holding one valid account could reset their IP counter between guesses at others.
- Failed 2FA codes and recovery codes count on the same counters (§12.3). Password-reset *requests* are rate limited by 06 §12 (5 per minute per IP and per identifier) but do not count toward sign-in lockout.
- This ladder is 07 §6.1's "progressive lockout" and subsumes 06 §12's 5-per-minute sign-in limit: the fifth failure within any window already triggers the first lockout. The sign-in form shows the wait ("Try again in 5 minutes") as a form error; there is no JSON sign-in endpoint, so 06 §12's 429 would apply only if one is added.

### 6.3 Users in more than one company

02 §4.4 allows a user to belong to several companies (a buying group, an agent). Decided 2026-09-24:

- **One approved company** → no choice; that company is the identity (§4.1).
- **More than one** → after sign-in (§6.1 step 8) the user **must choose** before reaching any page that prices or carts. The choice is held in the session and shown in the header; switching is available from the header and re-resolves the cart owner and prices without merging carts between companies.
- **Not persisted.** The choice lasts for the session; the next sign-in asks again. No `users.last_company_id` (02 §17.5).
- Only `approved` companies are offered. A company that is `suspended` (05.2 §9) is still offered — its users can see invoices and pay by card — but is labelled.

`CartOwnerResolver` currently picks the lowest `company_id`, as its docblock says, pending this spec. It must instead read the session's chosen company; that is an implementation change for when this spec is signed off.

## 7. Unapproved applicants

**Yes, an applicant can sign in.** Nothing in 05.2 prevents it, and 05.2 §4's "applicant sees" column describes status pages an applicant needs to reach. §5.1 gives every self-registered applicant a login.

What they see:

| Area | Behaviour |
|---|---|
| Application status | A status page with the 05.2 §4 wording for the current state. `info_requested` shows the reviewer's request and the response form (the same form the 05.2 §5.5 tokenised email link opens; either route works) |
| Catalogue and order pad | Base prices, with the persistent notice *"Trade prices shown after approval"* (05.2 §5.3). This is the same view as a signed-out visitor, but it follows the *applicant* rule, not the §14 flag: 05.2 §5.3 specifies base prices for unapproved visitors, and hiding them from someone who has already applied loses the planning benefit U3 describes |
| Cart | Allowed. The cart is theirs (`carts.user_id`), holds no prices (02 §14.3), and is re-priced on the next load after approval with the change shown (05.2 §12) |
| Checkout | Blocked, with a blocker naming the reason (`application_pending`) and linking to the status page. Checkout preview (06 §9.2) includes the blocker so the pad can show it before the buyer gets that far |
| Account pages | Profile, password, 2FA (§12), email verification (§11) |

**On approval** (05.2 §5.6) the applicant becomes a trade user on their next request: the company now exists and `company_users` links them. Their open sessions carry on; prices change on the next page load, which is why 05.2 §5.6 flushes the pricing cache.

**On rejection** (05.2 §5.7) the user keeps their login. They see the rejection message and, once the cooling period ends or the rejection is marked `remediable`, the option to re-apply. Meanwhile they are a **public customer** (§5.2): base prices, card or prepay, checkout open once their email is verified.

**On withdrawal** the same as rejection, without a cooling period.

## 8. Guest cart merge at login

**Already implemented**: `App\Listeners\MergeGuestCartOnLogin` → `CartService::mergeGuestCart()`, with the guest identity from `App\Http\Support\CartContext`. This section documents what the code does, so that later changes are made deliberately.

### 8.1 The guest token

A guest's cart is keyed by `carts.session_token` (02 §14.3). The token is a random 64-character string kept **in the server-side session** under `cart.session_token`. It is never the Laravel session id and is never sent to the browser. Because it lives in the session's data rather than being the session's id, it survives the `session()->regenerate()` that sign-in performs (§6.1 step 6). A guest who has only *read* a cart gets no token and no cart row. The token is created on the first write.

### 8.2 What happens on the `Login` event

Synchronously, inside the sign-in request, so the first page after signing in already shows the merged cart:

1. The guest token is **pulled** from the session, so it is removed whatever the outcome. From here on the cart is found by company or user. A token left in the session would silently start a fresh guest cart after logout.
2. No token, or no session → nothing to do.
3. The signed-in user's cart owner is resolved (`CartOwnerResolver`: the company if they have one, else the user). **For a user in several companies this must wait for the company choice** (§6.1 step 8, §6.3): see §8.4.
4. In one transaction, under the same per-owner lock `CartService::cartFor()` takes, so a merge cannot race a first add into creating two carts:
   - **No guest cart** → the owner's cart, if any, is untouched.
   - **Owner has no cart** → the guest cart is **adopted in place**: `company_id` and `user_id` are filled in, and line ids are unchanged.
   - **Owner already has a cart** → every guest line is added to it with `addLine()`'s summing rule: the same SKU and pack **add their quantities** (the 05.1 §7.1 "duplicate — merged" rule). Lines are applied in `(sku_id, pack_id)` order. The guest cart is then deleted, and its lines cascade.

A guest token can never reach a cart that has already been adopted. Guest lookups also require `company_id IS NULL AND user_id IS NULL`.

### 8.3 Consequences worth knowing

- **Quantities sum, never replace.** A buyer who had 3 outers in their company cart and adds 2 more as a guest ends with 5. This is intended ("add 5 more" semantics). The pad shows the merged result on the first page after sign-in.
- **Never before the second factor.** The merge runs on `Login`. The sign-in implementation must fire that event only after 2FA succeeds (§6.1 step 7), so that a password alone never moves a cart onto an account.
- **Company carts are shared.** A buyer's guest lines merge into their *company's* cart, which every user on that account sees (05.1 §10: last write wins on a line).
- **Staff sign-ins run it too.** A staff user without a company gets a user-owned cart. This is harmless, and there is usually no guest token anyway.
- **A `viewer`** (05.2 §10: no ordering) currently has guest lines merged into their company's cart like anyone else. ⚑4. The reviewer should decide whether a viewer's guest cart is discarded, kept as a user-owned cart, or merged as now.
- **Re-pricing is automatic.** Cart lines hold no prices (02 §14.3), so the merged cart prices at the signed-in identity's tier on the next render. 05.2 §12 also requires that the price change is **shown**; that indicator is not built yet.

### 8.4 Required change: merge after the company choice

Today the merge runs inside the `Login` event and `CartOwnerResolver` picks the lowest `company_id`. Once §6.3 is built, a multi-company user's guest cart must merge into the company they **choose**, which is only known after step 8 of §6.1. So, when this spec is implemented:

- **One company or none** → unchanged: merge on `Login`.
- **Several companies** → the listener leaves the guest token in the session; the company choice (§6.3) performs the merge into the chosen company's cart and then pulls the token. Switching company later never merges again.

The merge rules in §8.2 step 4 are unchanged.

## 9. Invited users

Invitations are rows in `company_invitations` (02 §17.1, DRAFT; decided 2026-09-24). Nothing is granted until the invitee accepts: no `users` row for a new person, no `company_users` row for anyone.

### 9.1 Who invites whom

| Inviter | May invite | Into |
|---|---|---|
| Company `owner` | Any `company_users` role, with `order_limit_minor` and `requires_approval` set on the invitation | Their own company |
| Administrator | As above | Any company |
| Anyone else | No one | — |

Staff are not invited this way (§5.3).

**Owners inviting owners** is allowed; 05.2 §10 gives owners "manage users" without restriction. One invariant is proposed (⚑5): **a company always keeps at least one active owner.** The last owner cannot be removed, demoted or suspended, which prevents an account that nobody can administer.

### 9.2 Flow

```
Owner submits email, first and last name, role, limit, requires_approval
  (Form Request; Policy: CompanyInvitationPolicy::create)
  → any open invitation for the same (company, email) is revoked
  → insert company_invitations (token_hash = SHA-256 of a random 64-char token,
    expires_at = now() + 7 days ⚑6a)
  → email the link carrying the token

Invitee opens the link — the row must be open: not accepted, not revoked, not expired.

  Email belongs to no user:
    → form: password (§5.4), optional 2FA enrolment
    → one transaction: insert users (status 'active', email_verified_at = now() —
      the link proves mailbox control); insert company_users from the invitation's
      role/limit/requires_approval; set accepted_at, accepted_by_user_id
    → signed in (§6.1 from step 6)

  Email belongs to an existing user:
    → they sign in normally if not already (password, 2FA)
    → one transaction: insert company_users; set accepted_at, accepted_by_user_id
    → no new account, no password change; if they now belong to several
      companies, §6.3 applies
```

The signed-in user must hold the invitation's email to accept it: a link forwarded to, or opened by, someone signed in as another address is refused with an explanation, never silently applied to the wrong account.

### 9.3 Managing invitations

The owner's users screen lists open invitations as **Invited**, with **Resend** (revokes the open row, issues a new one — so only the newest link works, 02 §17.1) and **Revoke** (`revoked_at`, `revoked_by_user_id`). Accepted, revoked and expired invitations stay as history. An expired invitation needs no clean-up; it is simply no longer open.

A person who registers or signs in while holding open invitations (`company_invitations_email_open_idx`) is shown them, and can accept from there.

## 10. Password reset

Policy is fixed by 07 §6.1: tokens are **single-use**, expire after **60 minutes**, and **using one invalidates all of the user's sessions**. Rate limit per 06 §12 (5/min per IP and per identifier).

```
1. User submits their email → always "If that address has an account, we've sent
   a link" (no enumeration)
2. If an active user exists: the password broker stores a hashed token in
   password_reset_tokens (02 §17.3; one per address, a new request replaces it)
   and emails the link
3. User opens the link → sets a new password (07 §6.1 rules)
4. In one transaction: update password_hash, delete the token, delete every
   session row of that user (§13.3)
5. Sign the user in on this device only, through the normal flow — including
   the 2FA challenge if enabled (§12). A reset never bypasses the second factor
```

A `pending` staff user (§5.3) who asks for a reset simply receives a set-your-password link — the same broker, the same token. A person with only an open *company invitation* has no user yet: they get the generic response and no email, and use the invitation link (§9). `suspended` and `closed` users get the generic response and no email.

## 11. Email verification

`users.email_verified_at` (02 §4.2).

| Identity | How verified | What waits for verification |
|---|---|---|
| Self-registered applicant | Emailed link, signed, 24-hour expiry | The application is **not placed in the review queue** until verified. A reviewer should not spend time on an address nobody reads, and 05.2 §5.1 already requires "deliverability" |
| Public customer | Emailed link, signed, 24-hour expiry | Checkout |
| Invited user | Accepting the invitation (§9.2) | Nothing further |
| Staff | Setting their password from the onboarding link (§5.3) | Nothing further |
| Any user changing email | Link to the **new** address; the old address is notified | The change itself: the old email stays in force until the new one is verified |

An unverified user can still sign in, browse, build a cart and resend the link. The verification link is not a sign-in link: opening it on another device verifies the address without creating a session.

## 12. Two-factor authentication

### 12.1 Who

07 §6.1: **mandatory for every staff role** (`admin`, `accounts`, `purchasing`, `rep`, `warehouse`, `sales_manager`, 02 §14.1). **Optional for trade users**, encouraged for company owners.

- **Staff.** A user holding any `role_user` row cannot reach any admin page or staff API until 2FA is enabled. On first sign-in they are sent to enrolment and nothing else is reachable. Granting a staff role to an existing user without 2FA forces enrolment on their next request. This also applies to the storefront for that user (§4.1: the stricter posture wins).
- **Trade users.** Enrolment is offered in account settings. Owners see a standing prompt until they enrol. Whether an owner may *require* 2FA for their buyers is not specified anywhere (⚑9).

### 12.2 Method

TOTP (RFC 6238, authenticator app) against `users.two_factor_secret` (stored encrypted), with `users.two_factor_enabled` set only after the user confirms a first code.

**Recovery codes are required** (decided 2026-09-24): without them a lost phone locks the user out permanently. They are rows in `user_two_factor_recovery_codes` (02 §17.2, DRAFT), one per code, hashed with Argon2id and spent by setting `used_at`.

- **Issued at enrolment**, shown once, with a prompt to store them; enrolment is not complete until the user confirms they have saved them.
- **Regenerable** from account settings after re-entering the password; regenerating replaces the whole set (02 §17.2).
- **A standing warning** when two or fewer unused codes remain.
- Using a code signs the user in and is audited and notified (§15).

SMS is not offered: it is weaker, and it would add a processor under 07 §7.5.

### 12.3 Challenge and recovery

- The challenge runs after the password succeeds and before the session is authenticated (§6.1 step 5). Failed codes, TOTP or recovery, count toward the same lockout counters (§6.2).
- **Lost device, staff:** an administrator resets the user's 2FA. The reset is audited (07 §6.5) and forces re-enrolment on the next sign-in. An administrator cannot reset their own.
- **Lost device, trade user:** a recovery code; failing that, an administrator reset after identity checks. The identity-check procedure is operational and not defined here (⚑9).

## 13. Sessions

### 13.1 Timeouts — 07 §6.1

| Identity | Idle timeout |
|---|---|
| Customer (applicant, trade user, public customer) | 12 hours |
| Staff (any `role_user` row) | 4 hours |
| Admin (`admin` role) | 1 hour |
| **Absolute maximum, everyone** | 7 days from sign-in |

The strictest applicable row wins: an `admin` who is also a trade buyer times out after an hour everywhere.

**Implementation note.** Laravel's `session.lifetime` is one global idle value. It is set to the longest idle limit (12 hours). A middleware then enforces the shorter per-identity limit and the 7-day ceiling, using two timestamps kept in the session: last activity and signed-in-at. Expiry signs the user out, keeps the intended URL, and returns them to the sign-in page with a notice. It never discards a cart, which is server-side (02 §14.3).

### 13.2 "Remember me"

**Not offered at launch.** `users` has no `remember_token` column (02 §4.2), and a persistent-login cookie would have to be capped at 7 days anyway to respect the absolute maximum. The idle limits above already cover a working day. Adding it later is a 02 amendment.

### 13.3 Ending sessions

- **Sign-out** invalidates the session and regenerates the CSRF token.
- **Session store: the database driver** (decided 2026-09-24), Laravel's default `sessions` table (02 §17.4). It is already the configured default in `config/session.php`. Its `user_id` column is what lets the next two rules end a user's sessions in one statement.
- **Password change or reset** ends every other session (07 §6.1): the user's `sessions` rows are deleted, except the current one on a change. Laravel's `AuthenticateSession` middleware — which compares a stored password hash on each request — stays in both the admin panel and the storefront `web` group as a second line.
- **User suspended or closed** → their `sessions` rows are deleted in the same transaction; the next request is unauthenticated (§4.2).

## 14. What a logged-out visitor sees on the order pad

05.2 §5.3 specifies **base prices with a persistent notice**, *"Trade prices shown after approval"*, and blocked checkout. 05.2 §15 Q1 records the alternative, **no prices at all**, as "a configuration flag, not a rebuild". No key is named anywhere, so one is proposed:

| | |
|---|---|
| Key | `catalogue.guest_price_visibility` — **proposed** (⚑11) |
| Type | `text` (02 §2.7 `value_type`) |
| Values | `base_with_notice` (default, 05.2 §5.3) · `hidden` |
| Scope | `global` only — a logged-out visitor has no company or location to scope by |
| Code default | `base_with_notice` |

| Value | Order pad for a logged-out visitor |
|---|---|
| `base_with_notice` | Full pad: search, filters, stock, packs, **base** prices and break tables (03 §4.2 rank 5), local recompute and footer totals (05.1 §5). A persistent banner: *"Trade prices shown after approval — sign in or apply for a trade account."* Cart building allowed (guest cart, §8). "Add to cart" works; checkout asks them to sign in or apply |
| `hidden` | Rows, packs and stock remain (discovery), but price, break and line-total columns, footer totals and spend or delivery progress are replaced by *"Sign in or apply to see prices."* `/pricing/bulk-resolve` refuses unauthenticated callers (401), so prices are withheld by the server, not merely hidden by the UI (01 §4: "never by hiding UI"). Cart building remains, since the pad is still useful as a list |

In both modes, **stock is shown**. Exact figures are a trade requirement (05.1 §4.3), and hiding stock was not part of the 05.2 decision. The reviewer may want stock gated too (⚑11).

The flag governs **logged-out visitors only**. A signed-in applicant always sees base prices with the notice (§7), and a trade user always sees their own prices.

## 15. Audit and notifications

**Audit (07 §6.5)** — actor, action, subject, IP, user agent, timestamp; append-only; 7-year retention. Recorded events:

sign-in success · sign-in failure (identifier, not password) · lockout · sign-out · session expiry · password change · password reset requested and completed · 2FA enrolled, disabled, reset by an administrator, recovery code used · email change · user invited, invitation accepted, revoked · role granted or revoked (staff and company) · user suspended, reinstated or closed.

The audit log table itself is a blocking gap tracked in ROADMAP §18. These events are specified here so that it can record them once it exists.

**Notifications** — delivered through 05.12 (unwritten; templates and channels are its concern):

| Event | To |
|---|---|

| Verify email | User |
| Invitation / added to a company | Invitee |
| Invitation accepted | Inviting owner |
| Password reset link | User |
| Password changed | User (security notice) |
| 2FA enabled or disabled, or reset by an administrator | User (security notice) |
| Sign-in from a new device ⚑12 | User |
| Email changed | Old and new address |

## 16. Edge cases

| Case | Behaviour |
|---|---|
| Applicant approved while signed in | Next request is as a trade user; prices change on the next load (§7) |
| Applicant signs in with a guest cart | Merged into their user-owned cart (§8). On approval that cart is **not** moved to the company automatically ⚑13: `carts` has one owner, and 05.2 §5.6 does not mention carts |
| Invitee's email has open invitations from two companies | Each is accepted separately; the first creates the user, the second links it. §6.3 applies from then on |
| Invitation link opened after expiry, revocation or a resend | Refused with "this invitation is no longer valid — ask {company} to send a new one"; nothing is created |
| Invitation opened while signed in as a different email | Refused; the invitee must sign in as the invited address (§9.2) |
| Owner revokes an invitation after it was accepted | The revoke is refused; removing a member is a separate, audited action |
| Last owner tries to leave | Refused (⚑5) |
| User removed from their only company while signed in | Next request finds no company: they become a public customer (§5.2), and their company's cart stays with the company |
| Multi-company user removed from the company chosen for this session | Next request returns them to the company choice (§6.3), or straight to their remaining company if only one is left |
| Lockout on an IP shared by many buyers (an office NAT) | Each buyer's identifier counter is separate, but the IP counter is shared: repeated failures by one person can lock the office out for up to 30 minutes. Accepted — 07 §6.1 requires the per-IP limit |
| Company suspended while its user is signed in | Session unaffected; on-account checkout blocked (05.2 §9) |
| Staff role granted mid-session | Staff 2FA and session limits apply on the next request (§12.1, §13.1) |
| Password reset while a checkout is in flight on another device | That device's session ends on its next request. The checkout either committed or did not (one transaction, 04 §4), never half-applied |
| Guest token present but the guest cart was already adopted elsewhere | Nothing merged; guest lookups exclude owned carts (§8.2) |
| Same email registers twice at once | `users_email_uq` guarantees one wins; the other receives the "you already have an account" email (§5.1) |

## 17. Test matrix

**Flows:** apply-and-register creates user plus application in one transaction, and neither exists if either fails · existing email gets the no-enumeration response and an email, not an on-screen error · applicant signs in, sees status, base prices and notice, and checkout preview carries `application_pending` · `info_requested` answerable from both the status page and the tokenised link · approval links the existing user as `owner` and prices change on the next load · rejected applicant keeps their login and can re-apply after the cooling period.

**Invitations:** owner invites a new email → one `company_invitations` row, no `users` or `company_users` row until acceptance · acceptance creates the user as `active` and verified and copies role/limit/`requires_approval` · invite of an existing user links it, no new account, no password change · resend revokes the previous row and only the newest link works · revoked, expired and accepted links refused · link refused for a user signed in as another email · the stored value is a SHA-256 hash, never the token · non-owner cannot invite (403, Policy) · last owner cannot be removed.

**Credentials:** identical responses for wrong password, unknown email and suspended user (body and timing within tolerance) · reset token single-use, rejected after 60 minutes, all other `sessions` rows deleted on use · reset does not bypass 2FA · breached password refused **with no outbound network call** (the test runs with outbound HTTP blocked).

**Lockout:** 5 failures → 1 min, 10 → 5 min, 15 and beyond → 30 min, never longer · per-IP and per-identifier counters independent · unknown identifiers locked identically to known ones · success clears the identifier counter, not the IP counter · failed 2FA and recovery codes count · nothing written to the database (counters in cache only).

**Company choice:** one company → no prompt · several → prompt before any priced page; unapproved companies not offered · choice not persisted — asked again at the next sign-in · a multi-company user's guest cart merges into the **chosen** company's cart, once (§8.4).

**2FA:** staff user cannot reach any `/admin` route or staff API before enrolment · role granted mid-session forces enrolment · recovery code single-use · administrator reset audited, and an administrator cannot reset their own.

**Sessions:** idle expiry at 12 h (customer), 4 h (staff), 1 h (admin), with the strictest winning for dual identities · absolute expiry at 7 days despite continuous activity · cart intact after expiry and sign-in · suspension deletes the user's `sessions` rows.

**Public customers:** register without an application → `active`, no company · checkout blocked until email verified, then card/prepay only (`on_account` refused) · applying makes them an applicant with checkout blocked; rejection returns them to public buying.

**Recovery codes:** issued at enrolment, each usable once (`used_at`), stored as Argon2id hashes · regeneration replaces the whole set · low-codes warning at two or fewer.

**Guest cart merge** (partly covered by existing `CartServiceTest`/`CartApiTest`): adopt in place when the owner has no cart · sum into the existing cart · token pulled in every outcome · no merge when 2FA is abandoned · concurrent merge and first add produce one cart.

**Guest price visibility:** `base_with_notice` shows base prices and the banner · `hidden` returns 401 from `/pricing/bulk-resolve` for guests and the pad shows no figures · the flag has no effect on signed-in applicants or trade users.

## 20. Implementation status (2026-09-24)

**Built:** checkout blockers for an open application (`application_pending`, §7), an unverified public customer (§11), a guest (§4.1) and a company `viewer` — reported by checkout preview and enforced by `POST /checkout` (06 §9.3); registration (trade apply-and-register, public), sign-in and sign-out on one page for everyone, lockout (§6.2), password reset and staff first-password (§10, §5.3), email verification (§11), 2FA enrolment, challenge, recovery codes, regeneration and opt-out for non-staff (§12), mandatory staff 2FA on every route including the admin panel, company choice with the guest-cart merge moved after it (§6.3, §8.4), session limits and suspension (§13), Argon2id hashing, the offline breached-password list and its quarterly refresh.

**Deliberate implementation details worth knowing:**

- **Laravel 11 advisories.** Two unpatched framework advisories touch this module; both are designed around rather than relied on. The verification link (§11) is an HMAC over user, email and expiry checked in the controller, not a Laravel temporary signed route (GHSA-crmm-hgp2-wgrp, path confusion). Every email field refuses CR and LF before the `email` rule runs (GHSA-5vg9-5847-vvmq, CRLF injection). Both are fixed only in Laravel 12.60+/13.x — upgrading is a stack decision (CLAUDE.md names Laravel 11).
- **TOTP** is implemented in `App\Domain\Identity\Totp` (RFC 6238, verified against the RFC's vectors), with replay protection per user; no 2FA package was added.
- **No QR code** on the enrolment page: rendering one needs a library outside the approved stack. The key is shown for typing and as an `otpauth://` link, which opens the authenticator directly on a phone.
- **Redis client:** `predis/predis`. The deployed PHP build has no phpredis extension.
- **Staff 2FA** is enforced in middleware on the web group, the `/api` group and the admin panel; a staff user without it reaches only enrolment and sign-out.

**Not built yet:**

- Invitation flows (§9) — the table exists, the screens and emails do not.
- The applicant's status page and the signed-in "apply for a trade account" form (§5.1, §7).
- An administrator reset of a user's 2FA (§12.3), and suspending users from the admin panel (§4.2 — the enforcement exists).
- The audit events in §15 — blocked on the audit log table (ROADMAP §18).
- Guest price visibility (§14) — the flag is still an open question (⚑11); logged-out visitors see base prices, the specified default.
